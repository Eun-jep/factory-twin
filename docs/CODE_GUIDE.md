# 코드 이해 가이드

이 프로젝트를 "내가 만들었고, 설명할 수 있다"로 만들기 위한 문서입니다.
코드 줄 번호 대신 **함수 이름**으로 안내합니다 (코드를 고쳐도 맞게 하려고).

- 규모: 시뮬레이터 463줄, 수집 서버 2,243줄, 웹 화면 2,441줄(3D 장면 `scene.js`는 784줄, 공장 배경 `factory_env.js` 302줄),
  시험 약 4,150줄 (Python 시험 308개 + JS 시험 76개), 시험 도구 약 560줄(`tools/`)
- 읽는 순서 추천: `collector/modbus.py` -> `device.py` -> `alarms.py` -> `store.py`
  -> `simulator/robot_sim.py` -> `webfeed.py` -> `web/app.js` -> `web/robot_math.js` -> `web/agv_logic.js` -> `web/factory_logic.js` -> `web/factory_env.js` -> `web/scene.js`
- 이 문서가 맞는지 의심되면 코드와 시험이 우선입니다. 시험(`python -m unittest discover -s tests`)이 통과하면
  아래 설명 중 동작에 관한 부분이 맞다는 근거가 됩니다.

## 2. 한 번의 읽기를 따라가기 (가장 중요)

수집 서버는 설비마다 0.5초에 한 번 아래를 반복합니다. 면접에서 "어떻게 동작하나요?"라고 물으면
이 순서로 설명하면 됩니다.

**1) 연결 확인** — `DeviceWorker.run()`의 반복문에서 연결이 없으면 `client.connect()`로 접속합니다.

**2) 요청 보내기** — `ModbusTcpClient.read_holding_registers(0, 10)`가 "0번부터 레지스터 10개를 읽어 줘"라는
12바이트를 만듭니다 (`build_read_request`). 예를 들어 트랜잭션 번호 42라면:

```
00 2A | 00 00 | 00 06 | 01 | 03 | 00 00 | 00 0A
  |      |       |      |     |     |       └ 개수: 10
  |      |       |      |     |     └ 시작 주소: 0
  |      |       |      |     └ 기능 코드 3 (Holding Register 읽기)
  |      |       |      └ 유닛 ID
  |      |       └ 길이: 뒤에 오는 바이트 수 (유닛 ID 1 + 기능 코드 이하 5 = 6)
  |      └ 프로토콜 ID (항상 0)
  └ 트랜잭션 번호 (요청과 응답을 짝지으려고 매 요청마다 1씩 올린다)
앞의 7바이트를 MBAP 헤더, 뒤의 5바이트를 PDU라고 부른다.
```

**3) 응답 받기와 검사** — 먼저 헤더 7바이트를 읽고 `parse_header`가 검사합니다.
프로토콜 ID가 0인가, 길이가 정상 범위(2~253)인가, 트랜잭션 번호와 유닛 ID가 요청과 같은가.
통과하면 나머지 `길이-1` 바이트(PDU)를 읽고 `parse_read_response`가 검사합니다.
설비가 예외 코드로 응답했는가(기능 코드에 0x80이 붙음), 바이트 수 필드가 `개수x2`와 같은가.
레지스터 10개를 읽으면 응답은 `7 + 22 = 29바이트`입니다 (기능 1 + 바이트 수 1 + 데이터 20).

**4) 값 해석** — `parse_registers`가 숫자 10개를 의미 있는 값으로 바꿉니다. 관절 각도는 `0.1도` 단위라
`452`는 `45.2도`입니다. 단계 번호나 상태 값이 범위를 벗어나면 `ValueError`를 내고, 이것도 "읽기 실패"로 처리합니다.

**5) 읽기 성공 처리** — `DeviceWorker._record_success`가 통계를 갱신하고 `on_snapshot`을 부릅니다.
`collector/__main__.py`의 `on_snapshot`이 세 가지를 합니다.
`store.add_sample`(DB 저장), `manager.on_snapshot`(알람 판정), `feed.publish`(브라우저 전송).

**6) 다음 일정까지 쉬기 (고정 주기)** — 읽기가 **끝난 뒤** 0.5초 쉬는 방식이면 설비 응답이 느릴수록 주기가 늘어납니다
(응답 0.3초 + 쉬기 0.5초 = 0.8초). 그래서 `다음에 읽을 시각`을 정해 두고 **그 시각까지만** 쉽니다 (`next_schedule`).
응답이 주기보다 길어 일정을 놓쳤을 때는 밀린 만큼 몰아서 읽지 않고(설비에 부담) 지금을 새 기준으로 삼습니다.
설비가 여러 대면 모두 같은 순간에 읽고 저장하지 않도록 설비마다 시작을 엇갈립니다 (`stagger_delay`, 한 주기 안에 고르게).

**실패하면** — 시간 초과, 연결 끊김, 규격 위반(깨진 응답), 이상한 값은 모두 같은 길로 갑니다.
연결을 닫고(`client.close()`) `_wait_backoff`로 1초, 2초, 4초(최대) 쉰 뒤 다시 접속합니다 (상한은 `--backoff-max`, 기본 4초).
읽기에 한 번 성공하면 대기 시간은 1초로, 일정도 새로 시작합니다. 설비가 "예외 응답"만 보낸 경우는 연결이 정상이므로
재접속 없이 다음 주기에 다시 읽습니다.

## 3. 파일별 설명

### `collector/modbus.py` — 통신
- `build_read_request`, `parse_header`, `parse_read_response`: 소켓과 무관한 **순수 함수**라서 시험하기 쉽습니다.
- `ModbusTcpClient`: 비동기 클라이언트. 오류를 네 종류로 나눕니다.

| 오류 | 뜻 | 수집 서버의 대응 |
|---|---|---|
| `ModbusTimeout` | 제한 시간(1초) 안에 응답이 없음 | 연결을 닫고 재접속 |
| `ModbusConnectionError` | 접속 거부, 연결이 끊김 | 연결을 닫고 재접속 |
| `ModbusProtocolError` | 규격에 맞지 않는 응답 | 연결을 닫고 재접속 |
| `ModbusExceptionResponse` | 설비가 "그 주소는 없다" 같은 예외로 응답 | 연결 유지, 다음 주기에 재시도 |

- **왜 시간 초과 뒤에 연결을 닫을까?** 늦게 도착한 응답이 다음 요청의 응답과 뒤섞이는 것을 막기 위해서입니다.
  트랜잭션 번호로 걸러 낼 수도 있지만, 닫고 새로 연결하는 쪽이 단순하고 확실합니다.

### `collector/models.py` — 값 해석
레지스터 맵(어느 주소에 무엇이 있는지)과 `Snapshot`(해석된 값)이 있습니다. 시뮬레이터와 같은 맵을 써야 하므로
시험이 두 파일의 주소가 일치하는지 확인합니다 (`test_register_map_matches_simulator`).

### `collector/device.py` — 설비 1대를 맡는 워커
- 설비마다 `DeviceWorker`가 하나씩 있고, **각자 자기 연결·상태·통계**를 가집니다. 이것이 **장애 격리**의 핵심입니다.
  ARM-02가 끊겨도 ARM-01·03의 워커는 영향을 받지 않습니다 (시험과 실제로 확인).
- `ConnState`: 접속 중, 정상, 재접속 대기, 중지.
- 끊김은 두 경로로 알아챕니다. 읽는 도중 끊기면 `read_failed`, 쉬는 사이에 연결이 리셋되면 `disconnected`.
- `DeviceStats.data_age`: 마지막 값을 받은 지 몇 초인지. 끊긴 설비의 마지막 값을 현재 값처럼 보이지 않게 하려고 있습니다.

### `collector/alarms.py` — 알람
| 알람 | 등급 | 조건 |
|---|---|---|
| EQUIPMENT_FAULT | P1 | 설비가 상태 '이상'(정지)을 보고 |
| COMM_LOST | P1 | 통신 실패가 연속 3회 이상 |
| TEMP_WARNING | P2 | 설비가 상태 '주의'를 보고 |
| COUNTER_RESET | P3 | 생산 카운트가 줄어듦 (설비 재시작 추정) |

규칙 네 가지를 이해하면 됩니다.
1. **중복 방지**: 같은 설비·종류의 알람이 열려 있으면 새로 만들지 않고 값만 갱신합니다.
2. **해제 지연(3초)**: 조건이 사라져도 3초 동안 계속 사라져 있어야 해제합니다. 기준선 근처에서 값이 흔들릴 때
   알람이 켜졌다 꺼졌다 하는 것(채터링)을 막습니다.
3. **확인(ACK)과 해제는 독립**: 값이 정상으로 돌아와도 사람이 확인하기 전에는 닫히지 않습니다.
   상태는 `활성·미확인 -> 활성·확인됨 -> 종료`, 또는 `활성·미확인 -> 해제됨·미확인 -> 종료`.
4. **반복 묶기(60초)**: 해제된 지 60초 안에 같은 알람이 다시 발생했고 **아직 아무도 확인하지 않았다면**
   새로 만들지 않고 기존 알람을 다시 열면서 반복 횟수를 올립니다. 이미 확인된 알람은 다시 열지 않고 새 알람으로
   만듭니다 (확인한 사람이 재발생을 놓치면 안 되니까).
   같은 조건 60초 측정에서 알람이 27줄 -> 6줄로 줄었고, 발생 횟수 합은 27로 같았습니다 (이력 손실 없음).

### `collector/store.py` — 저장
- SQLite 한 파일(`data/factory.db`)에 세 테이블: `samples`(측정값), `events`(통신 이벤트), `alarms`(알람).
- `count_delta`: 생산 카운트는 16비트 누적 값이라 줄어드는 경우가 두 가지입니다.
  65536에서 0으로 **한 바퀴 돎**(이어서 셈)과 설비 **재시작으로 초기화**(재시작 후 센 개수만 더함).
  `production_between`이 이걸 반영해서 생산량을 정확히 셉니다.
- `_migrate`: 이전 버전으로 만든 DB를 열 때 새 열을 추가합니다. 기존 데이터는 보존합니다.

### `collector/webfeed.py` — 브라우저 전송
- **WebSocket을 라이브러리 없이 직접 구현**했습니다 (RFC 6455). 핸드셰이크(`accept_key`), 프레임 만들기
  (`encode_frame`), 읽기(`read_frame`: 클라이언트 프레임은 반드시 마스킹되어 있어야 함).
- 한 포트에서 두 가지를 합니다: 일반 GET이면 `web/`의 정적 파일, `/ws`면 WebSocket.
- **느린 브라우저가 수집을 붙잡지 않게**: 접속자마다 크기가 정해진 대기열을 두고, 가득 차면 오래된 메시지부터
  버립니다. 5초 안에 보내지 못하면 그 접속을 끊습니다.
- **보안 규칙 세 가지**
  1. `Host` 헤더가 로컬 주소(127.0.0.1, localhost, ::1)가 아니면 거절 (DNS 리바인딩 방지).
  2. WebSocket은 `Origin`이 접속한 주소와 같을 때만 받음 (다른 웹사이트가 몰래 접속해 데이터를 읽는 것 방지).
  3. 정적 파일은 `web/` 폴더 밖으로 나갈 수 없음 (`../` 경로 차단).
  기본으로 127.0.0.1에만 열려 이 PC에서만 접속됩니다.
- 메시지 종류: `state`(전체 상태 + 지표, 접속할 때와 1초마다. **패킷 기록은 싣지 않습니다**: 설비당 2~3KB라서 설비 수에 비례해 커지므로 `/api/packet`으로 따로 가져갑니다), `snapshot`(값, 0.5초마다), `alarm`, `event`,
  그리고 브라우저 명령에 대한 답 `ack_result`/`error`. 접속할 때 오는 `hello`에는 최근 이벤트 30개도 들어 있습니다.
  `state`를 주기적으로 다시 보내는 이유는 개별 알림을 놓친 화면도 곧 맞는 상태가 되게 하려는 것입니다.

### `collector/packets.py` — 패킷 뷰어의 재료
- `modbus.py`가 한 번 주고받을 때마다 `Exchange`(보낸 바이트, 받은 바이트, 오류)를 남깁니다. 정상 기록(`last_exchange`)과
  실패 기록(`last_failed_exchange`)을 **따로** 둬서, 실패 직후 정상 응답이 와도 실패한 바이트를 계속 볼 수 있습니다.
- 이 파일은 그 바이트를 "어느 바이트가 무슨 뜻인지" 필드 목록으로 바꿉니다 (헤더 7바이트, 기능 코드, 시작 주소, 개수,
  레지스터 값). 예외 응답(0x80이 더해진 기능 코드)과 깨진 응답도 가능한 만큼 해석하고 못 하는 부분은 `error`로 표시합니다.
- 화면의 패킷 뷰어는 이 기록을 1초 방송이 아니라 `/api/packet?device=`로 **고른 설비 하나만** 가져갑니다 (`webfeed.packet_state`).
- 레지스터 이름은 응답 안의 **순서가 아니라 실제 주소**로 붙입니다 (시작 주소가 0이 아닐 때도 맞도록). 이 부분은 시험이
  한 번 잡아낸 실제 버그였습니다.

### `collector/stats.py` — 이력과 지표
- `history`: 최근 N분의 측정값을 차트용으로 줍니다. 점이 너무 많으면 `downsample`로 일정 간격으로 솎되 **마지막(최신) 점은
  항상 남기고 최대 개수는 지킵니다** (모든 크기·개수 조합을 시험).
- `availability`(가동률) = 이상이 아닌 상태로 읽은 표본 수 / 읽었어야 할 표본 수. 수집이 안 된 시간은 가동 안 한 것으로
  세므로 통신이 끊기면 가동률이 내려갑니다. 단, 그 설비의 **첫 표본 이전은 세지 않아서** 막 켠 직후에 낮게 나오지 않습니다.
- `compute_kpis`: 가동률, 생산량(카운트 한 바퀴·재시작 보정), 통신 성공률, 평균 응답, 재접속. `KpiCache`는 DB를 읽는
  계산이라 5초에 한 번만 다시 합니다.

### `collector/retention.py` — 측정값 보관 정책
- 설비 1대는 하루에 약 17만 건을 쌓고 건당 약 110바이트라서, 지우는 기능이 없으면 DB가 끝없이 커집니다(7단계 부하 시험에서 확인).
  그래서 **보관 기간(`--retention-days`, 기본 7일)이 지난 측정값과 통신 이벤트를 자동으로 지웁니다.** 0이면 지우지 않습니다.
- **알람은 지우지 않습니다.** 건수가 적고 "누가 언제 확인했는가"를 남기는 기록이기 때문입니다.
- 시작할 때 한 번, 그다음 1시간마다 정리합니다. 한 번에 설비마다 5,000건씩 지우고 사이사이 쉬어서(`prune_once`) 오래 쌓인 DB를
  처음 정리할 때도 수집이 멈추지 않습니다. 측정값 색인이 (설비, 시각) 순이라 설비별로 지워야 전체를 훑지 않고 빠릅니다
  (`Store.prune_old`). 보관 기간과 같은 시각의 행은 남깁니다(그보다 **오래된** 것만 지움).
- 정리가 실패해도(디스크 오류 등) 수집은 멈추지 않고 다음 주기에 다시 시도합니다.
- 알아둘 점: SQLite 파일 크기는 지운다고 줄지 않고 빈 공간을 다시 씁니다. 그래서 파일은 보관 기간 안의 양에서 더 커지지 않습니다.

### `collector/api.py`, `collector/commands.py` — 조회와 명령
- `api.py`: `/api/history`, `/api/events`, `/api/alarms`, `/api/packet`. 숫자 파라미터는 `int()` 대신 정규식 `-?[0-9]+`로 검사합니다
  (`int()`는 아랍 숫자 "٣"도 3으로 받아서, 시험이 잡아낸 뒤 고쳤습니다). 모르는 설비는 404, 잘못된 값은 400.
  SQL은 항상 `?` 자리표시자로 값을 넘기고, 설비 이름은 목록에 있는지 먼저 확인합니다.
- `commands.py`: 브라우저의 `ack`(알람 확인) 명령. 이름은 1~20자·제어문자 없음, id는 양의 정수(`True`도 거절).
  이미 확인된 알람이면 `ok:false`와 이유를 돌려줍니다.
- `webfeed.py`는 명령 한 개를 4096바이트로, 한 접속이 5초에 20개로 제한하고 넘으면 1008(정책 위반)로 끊습니다.
  JSON이 아니거나 처리 중 예외가 나도 접속은 유지하고 `error`로만 답합니다 (내부 내용은 로그에만).

### `simulator/` — 가상 설비
- `robot_sim.py`의 `RobotSim`: 통신과 무관한 순수 로직. `step(dt)`로 시간을 흘리고 `registers()`로 값을 읽습니다.
  사이클은 대기 -> 접근(1.5초) -> 집기(0.8초) -> 이동(2.0초) -> 놓기(0.8초) -> 복귀(1.5초), 약 6.6초.
  온도는 움직일 때 오르고 쉴 때 내립니다. 65도 주의, 80도 이상(정지), 70도 이하로 식으면 복구
  (**히스테리시스**: 올라갈 때와 내려올 때 기준이 다르게 해서 경계에서 흔들리지 않게 함).
- `modbus_sim.py`의 `SimServer`: 로봇 1대를 Modbus 서버로 노출합니다. 통신 장애를 일부러 낼 수 있습니다
  (`--delay-ms`, `--drop-every`, `--garbage-every`). 이미 쓰는 포트에서는 시작을 거부합니다.
- `run_all.py`: 로봇 6대(ARM-01~06)를 포트 5021~5026에 한 번에 띄웁니다. 수집기의 기본 설정도 같은 6대입니다.

### `web/` — 화면
- `app.js`: `/ws`에 연결하고, 메시지를 받아 화면을 고칩니다. 끊기면 1, 2, 4, 8초로 늘려 가며 다시 연결합니다
  (수집 서버가 설비에 재접속하는 방식과 같음). 화면에 글자를 넣을 때는 항상 `textContent`를 씁니다
  (`innerHTML`에 서버 데이터를 넣으면 섞인 HTML 태그가 실행될 수 있기 때문).
- 화면 구성(위에서 아래): 지표 띠(가동률·생산량·통신 성공률·평균 응답·재접속·열린 알람), 3D(가로 전체), 설비 카드(한 줄),
  알람 표(확인 버튼), 왼쪽 열(온도 차트, 통신 이벤트) + 오른쪽 열(패킷 뷰어). 좁은 화면에서는 한 열로 쌓입니다.
- **3D 카메라는 화면 모양에 맞춰 거리를 자동으로 정합니다** (`fitCamera`). 카메라 위치가 고정이면 화면이 좁아질 때 양옆 로봇이
  잘렸습니다. 세로 시야각이 정해져 있어 거리 d에서 보이는 가로 반쪽은 `d * tan(시야각/2) * 가로세로비`이므로, 보여야 할 폭에서
  거리를 거꾸로 계산합니다 (`robot_math.js`의 `fitDistance`, Node로 시험). 보는 방향은 그대로라 마우스로 돌린 각도는 유지됩니다.
  차트 가로축은 구간 전체가 아니라 실제 데이터가 시작된 시점부터 그립니다. 지표·패킷은 서버가 계산·해석해서 보내고 화면은 그리기만 합니다.
- **알람 표는 줄을 다시 만들지 않습니다.** `state`가 1초마다 오는데 표를 통째로 새로 만들면, 버튼을 누르는 순간
  (마우스를 누르고 떼는 사이)에 버튼이 교체되어 클릭이 사라집니다. 그래서 알람 번호별로 줄을 한 번만 만들고 글자만 고칩니다
  (실제로 처음 만든 버전에서 발견했고, 같은 버튼 요소가 유지되는지 브라우저에서 확인했습니다).
- 온도 차트는 라이브러리 없이 `canvas`에 직접 그립니다 (`/api/history`를 5초마다). 선은 그 시점의 설비 상태 색(정상 파랑,
  주의 노랑, 이상 빨강)이고 점선은 주의·이상 기준입니다. 설비를 바꿨을 때 늦게 도착한 옛 응답은 요청 번호로 버립니다.
- 패킷 뷰어: 서버가 나눠 준 필드를 바이트 색으로 나눠 보여 주고, 표의 줄과 바이트에 마우스를 올리면 함께 강조됩니다.
  '마지막 실패'는 읽는 도중 깨진 응답을 볼 수 있고, 접속 자체가 안 된 경우는 오간 바이트가 없어 비어 있습니다.
- 확인자 이름은 브라우저 저장소에 기억하지만, 저장이 막힌 환경에서도 화면은 동작하도록 `try/catch`로 감쌌습니다.
- 값이 오래됐거나 연결이 끊기면 카드를 흐리게 하고 "마지막 수신 N초 전 (값은 오래됨)"을 보여 줍니다.
- `scene.js`: Three.js로 로봇 팔 6대(두 가지 모양, 두 줄 배치)와 컨베이어를 그리고 서버 값대로 움직입니다 (아래 4-2에서 자세히).
- `bloom.js`: 빛 번짐(후처리)을 이어 붙이는 짧은 파일. `scene.js`가 따로 불러오므로 실패해도 나머지 화면은 정상입니다.
- `factory_env.js`: 공장 건물(바닥, 뒷벽, 철골 기둥, 천장 조명)과 벽에 걸린 모니터 3대를 그립니다. 모니터는 `canvas`에 그린 그림을 3D 판에 입힌 것입니다.
- `factory_logic.js`: 모니터에 보여 줄 값의 **계산만** 모은 파일 (상태별 개수, 지표 단계, 온도 추이의 그래프 좌표, 최근 알람 고르기). Node로 시험합니다.
- `agv_logic.js`: 상자 쌓기와 이동 로봇(AGV)의 **판단만** 모은 파일 (팔레트에 몇 개 쌓였나, AGV가 어디로 가서 언제 싣는가). Three.js 없이 Node.js로 시험합니다.
- `robot_math.js`: 3D와 상관없는 **계산만** 모은 파일 (각도 변환, 부드럽게 따라가기, 색 고르기, 배치, 경광등 깜빡임, 롤러 회전).
  Three.js를 쓰지 않아서 Node.js로 시험할 수 있습니다 (`tests/js/`).
- `vendor/`: Three.js 0.170.0을 **그대로** 가져온 파일 13개 (본체, OrbitControls, 라이선스, 그리고 빛 번짐용 `postprocessing/` 7개와 `shaders/` 3개).
  출처, 해시, 라이선스는 `vendor/VENDOR.md`에 있고, 시험이 파일이 바뀌지 않았는지 매번 확인합니다.
- `index.html`의 `importmap`: `OrbitControls.js`가 `from 'three'`라고 불러오는데 브라우저는 'three'가 어느 파일인지
  모릅니다. importmap이 "three는 `./vendor/three.module.min.js`"라고 알려 줍니다.
- 3D는 `import("./scene.js")`로 **따로** 불러오고 실패하면 안내만 보여 줍니다. 그래픽 가속이 안 되는 브라우저에서도
  카드와 알람 표는 계속 동작합니다 (실제로 파일을 빼고 확인).

## 4. 핵심 개념 쉬운 설명

**Modbus TCP란?** 공장 설비(PLC, 센서)가 값을 주고받는 오래된 산업용 통신 규격입니다. 아주 단순해서
"몇 번 주소의 값 몇 개를 줘"라는 요청과 응답으로만 이루어집니다. TCP 위에서 쓰는 것이 Modbus TCP입니다.

**비동기(asyncio)란?** 한 번에 한 가지 일만 하는 스레드가, 기다리는 시간(네트워크 응답 등)에 다른 일을 하는 방식입니다.
로봇 3대를 읽을 때 한 대의 응답을 기다리는 동안 다른 대의 요청을 보냅니다. `await`는 "여기서 기다리는 동안
다른 일을 해도 좋다"는 표시입니다. 스레드를 여러 개 만드는 것보다 가볍고, 공유 데이터 충돌 걱정이 적습니다.

**타임아웃이 왜 필요한가?** 설비가 응답하지 않아도 수집 서버가 영원히 기다리면 그 설비의 수집이 멈춥니다.
제한 시간(1초)을 두고 넘으면 실패로 처리해 다음 동작(재접속)으로 넘어갑니다.

**백오프(대기 시간을 늘려 가기)란?** 설비가 꺼져 있을 때 0.5초마다 접속을 시도하면 헛수고이고 서버에 부담입니다.
1, 2, 4초(최대)로 간격을 넓히면 낭비를 줄이면서도 설비가 돌아오면 최대 4초 안에 다시 붙습니다. (처음에는 상한이 8초였는데, 7단계 실측에서 복구가 최대 8초 늦을 수 있다는 것을 알고 4초로 줄였습니다.)

**장애 격리란?** 한 설비의 문제가 다른 설비로 번지지 않게 하는 설계입니다. 설비마다 워커, 연결, 상태를
따로 두었기 때문에 ARM-02가 끊겨도 ARM-01·03은 계속 읽습니다.

**알람 채터링이란?** 값이 기준선 근처에서 흔들려 알람이 켜졌다 꺼졌다를 반복하는 현상입니다. 현장에서는
같은 알람이 수십 줄 쌓여 정작 중요한 알람을 못 보게 됩니다. 해제 지연(3초)과 반복 묶기(60초)로 줄였습니다.

**SQLite의 WAL이란?** 쓰기를 별도 파일(`.db-wal`)에 먼저 기록해 두는 방식입니다. 프로그램이 갑자기 꺼져도
다음에 열 때 자동으로 복구되고, 읽는 쪽이 쓰는 쪽을 막지 않습니다. `data/` 폴더에 `.db-wal`, `.db-shm` 파일이
보이는 이유입니다.

**WebSocket이란?** 한 번 연결하면 서버가 브라우저로 데이터를 계속 밀어 줄 수 있는 연결입니다. 일반 HTTP는
브라우저가 물어볼 때만 답하지만, WebSocket은 서버가 값이 생길 때마다 바로 보낼 수 있어 실시간 화면에 적합합니다.
클라이언트가 보내는 프레임을 마스킹하게 한 것은 중간 장비(프록시)가 데이터를 오해하는 것을 막기 위한 규격입니다.

## 4-2. Three.js 쉬운 설명 (처음 보는 사람을 위한)

**Three.js란?** 브라우저에서 3D 그림을 그려 주는 자바스크립트 라이브러리입니다. 이 프로젝트에서는 도형(상자, 원기둥,
구)을 이어 붙여 로봇 팔을 만들고, 서버가 보낸 값대로 움직이게 하는 데만 씁니다. 3D 모델링(Blender 등)은 하지 않았습니다.

**꼭 알아야 할 다섯 가지**

| 개념 | 한 줄 설명 | 이 프로젝트에서 |
|---|---|---|
| Scene(장면) | 3D 물체를 올려 두는 무대 | 바닥, 로봇, 컨베이어를 올려 둠 |
| Camera(카메라) | 어디서 보는지 | 오른쪽 앞 위에서 살짝 비스듬히 내려다봄 (정면보다 입체적) |
| Renderer | 장면을 화면의 캔버스에 그리는 일꾼 | `renderer.render(scene, camera)` |
| Mesh | 물체 하나 = 모양(Geometry) + 재질(Material) | 원기둥+주황 재질 = 기둥 |
| 애니메이션 루프 | 매 프레임(1초에 약 60번) 값을 고치고 다시 그리는 반복 | `animate()` 함수 |

**이 프로젝트의 핵심 아이디어: 부모-자식.** 물체를 다른 물체 안에 넣으면 부모가 움직일 때 자식이 같이 움직입니다.

```
group (로봇 한 대. 팔 모양은 관절 팔과 스카라 팔 두 가지)
 ├─ 받침             경고 줄무늬 판 + 어두운 원통 + 볼트 8개 (고정)
 ├─ shoulder        <- 이 그룹을 y축으로 돌리면 아래가 전부 같이 돈다 (joint1, 어깨 회전)
 │    ├─ 기둥, 관절 몸통, 띠
 │    └─ elbow          <- 이 그룹을 z축으로 돌리면 팔과 집게가 같이 숙여진다 (joint2, 팔꿈치)
 │         ├─ 팔꿈치 관절 통, 팔(끝이 가는 원기둥), 중간 마디
 │         └─ hand          손목, 손바닥, 집게 (손가락 2개의 벌어짐은 위치로 표현)
 ├─ 롤러 컨베이어     옆 틀, 다리, 롤러 14개(속도에 맞춰 돈다), 위의 상자 3개
 ├─ 팔레트           위판 4장 + 밑받침 3개, 그 위에 쌓이는 상자 4개 (생산 카운트가 늘 때마다 하나씩 보임)
 ├─ 손에 든 상자      집기~놓기 단계 동안 집게에 매달림
 ├─ 안전 펜스        뒤와 양옆 기둥·가로대, 앞은 바닥에 노란 선만 (시야를 가리지 않게)
 ├─ 경광등           펜스 뒤쪽 기둥 위. 상태에 따라 색과 깜빡임이 바뀐다
 └─ 정보 카드         로봇 머리 위에 떠서 따라다니는 HTML 카드 (3D 물체가 아님)
```

외형은 전부 기본 도형(상자, 원기둥, 구, 도넛)을 조합한 것이고 외부 모델 파일은 쓰지 않았습니다. 같은 일을 하는 코드는
`part(부모, 모양, 재질, x, y, z)` 도우미 하나로 모았습니다. 도형을 만들어 붙이고 그림자를 켜는 일을 한 줄로 끝냅니다.

`shoulder.rotation.y = 값` 한 줄이면 기둥, 팔꿈치, 팔, 집게가 전부 같이 돕니다. 각 부품의 위치를 따로 계산하지 않아도 됩니다.

**서버 값이 3D가 되기까지**

```
서버 snapshot 메시지 (0.5초마다, 관절 각도는 '도' 단위)
   -> app.js showSnapshot  -> scene.js updateRobot: '목표' 값만 바꾼다 (robot_math.js의 각도 변환 사용)
   -> scene.js animate (매 프레임): '현재' 값이 '목표'를 조금씩 따라간다 (smoothTowards)
   -> 현재 값을 shoulder.rotation.y, elbow.rotation.z에 적용 -> renderer.render로 그린다
```

**왜 '목표'와 '현재'를 나눌까?** 서버 값은 0.5초에 한 번 오지만 화면은 1초에 60번 그립니다. 값이 올 때마다 팔을
그대로 옮기면 뚝뚝 끊깁니다. 그래서 값은 '목표'로만 기억하고, 화면이 매 프레임 그쪽으로 조금씩 다가가게 합니다.

**프레임 속도가 달라도 같은 속도로 움직이게 하는 방법.** `smoothTowards(현재, 목표, dt)`는 지난 프레임 이후 흐른 시간
`dt`를 반영한 지수 감쇠(`1 - e^(-rate x dt)`)를 씁니다. 이 식은 프레임을 반으로 쪼개 두 번 적용해도 한 번 적용한
것과 결과가 같아서, 느린 컴퓨터와 빠른 컴퓨터에서 움직임이 같습니다 (시험으로 확인: `tests/js`).

**각도 규칙 (`robot_math.js`)**
- `joint1`(어깨 회전): 서버 값 90도가 정면. 130도면 +40도 돌아 컨베이어 쪽, 50도면 -40도 돌아 팔레트 쪽.
- `joint2`(팔꿈치): 값이 클수록 팔이 수평에서 아래로 더 숙입니다 (z축 회전에서 음수가 아래라 부호를 뒤집음).
- 서버는 '도', Three.js는 '라디안'을 쓰므로 `x (파이/180)`을 곱합니다.

**상태 표현**: 정상 주황, 주의 노랑, 이상 빨강, 통신이 끊겨 값이 오래됨 회색. 끊긴 로봇은 마지막 자세 그대로
멈추고 컨베이어 상자와 롤러도 멈춥니다 (오래된 값을 현재 값처럼 보여 주지 않기 위해).

**경광등** (`robot_math.js`의 `beaconState`): 공장 설비 위에 다는 신호등입니다. 정상은 초록이 계속 켜져 있고, 주의는 노랑이
천천히(1.25초 주기), 이상은 빨강이 빠르게(0.5초 주기) 깜빡입니다. 통신이 끊기면 꺼집니다. 로봇 몸체 색과 따로 한 번 더 알려
주는 장치라서, 멀리서 보거나 색을 구분하기 어려워도 깜빡임으로 이상을 알아챌 수 있습니다. 시각 t를 받아 밝기를 돌려주는
순수 계산이라 같은 t에는 항상 같은 결과가 나오고, Node로 시험합니다.

**롤러 회전** (`rollerAngle`): 물건이 컨베이어 위를 가는 속도(mm/s)만큼 롤러 윗면도 같이 가도록 롤러 각도를
`이동 거리 / 반지름`만큼 줄입니다. 한 바퀴를 넘으면 0~2파이로 되돌립니다. 이상으로 속도가 0이면 롤러도 멈춥니다.

**로봇 위 정보 카드**: 로봇 머리 위에 이름, 상태, 온도, 가동률, 현재 단계를 보여 주는 작은 카드입니다. 3D 물체가 아니라
**평범한 HTML 요소**를 3D 화면 위에 겹쳐 놓은 것입니다. 그래서 글자가 선명하고 모양은 CSS(`.rcard`)로 정합니다.
따라다니는 원리는 이렇습니다. 매 프레임 로봇 머리 위 3D 점을 `project(camera)`로 카메라에 찍으면 -1~1 범위의 좌표가 나오고,
이것을 픽셀로 바꿔(`robot_math.js`의 `ndcToScreen`, 화면의 y축은 아래로 늘어나므로 뒤집음) 카드의 `transform`을 옮깁니다.
카메라를 돌리거나 로봇이 움직여도 카드가 같이 가는 이유입니다. 값은 서버 `snapshot`(온도, 단계)과 지표(가동률)에서 받고,
내용이 바뀔 때만 글자를 다시 씁니다. 글자는 `textContent`로만 넣어 서버 값이 HTML로 해석되지 않게 했습니다. 로봇 상태색(정상
초록, 주의 노랑, 이상 빨강, 끊김 회색)은 카드 왼쪽 띠와 상태 글자에 같이 씁니다. 화면이 700px보다 좁으면 이름·상태·온도만
남겨 카드끼리 겹치지 않게 합니다. 마우스는 카드를 통과해 아래 3D 캔버스로 가므로 카드가 있어도 돌리고 확대할 수 있습니다.

**로봇 모양 두 가지와 두 줄 배치**: 로봇 6대는 홀수 번호(ARM-01, 03, 05)가 **관절 팔**(높은 기둥 위에서 팔꿈치가 숙임), 짝수
번호(ARM-02, 04, 06)가 **스카라(SCARA) 팔**(낮고 굵은 기둥 위에서 마디 두 개가 수평으로 돌고 집게가 아래로 내려감)입니다.
- **모양은 서버 값이 아닙니다.** 서버는 모양을 모르고 두 종류 모두 같은 3가지 값(어깨 회전, 팔꿈치, 집게)만 보냅니다.
  모양은 설비 이름 끝 번호의 홀짝으로 화면이 정합니다(`robot_math.js`의 `robotKind`).
- **스카라가 관절 팔과 같은 위치를 집고 놓는 방법**: 관절 팔은 값으로 팔 끝 위치가 곧바로 정해집니다(방향 = 어깨 회전,
  수평 거리 = 팔 길이 x cos(숙인 각도)). 스카라는 마디 두 개가 수평으로만 돌아서, 같은 점에 닿으려면 두 관절 각도를 거꾸로
  계산해야 합니다(역운동학, `scaraPose`). 마디 길이(1.15, 1.0)로 닿을 수 있는 범위로 거리를 제한하고, 코사인 법칙으로
  팔꿈치 꺾임을, 아크탄젠트로 첫째 마디 방향을 구합니다. 시험에서 계산한 각도로 다시 팔 끝 위치를 구해(순운동학) 목표와
  같은지 확인합니다. 팔을 완전히 펴도 모자라는 대기 자세는 곧게 펴고 방향만 맞춥니다.
- **배치**: 3대까지는 한 줄, 4대부터는 두 줄입니다(`cellPlacement`). 가운데 길(AGV가 다니는 곳)을 두 줄이 마주 보고, 앞 줄은
  뒤돌려(y축 180도) 놓아 팔레트가 길 쪽을 향합니다. 뒤돌려 놓인 로봇의 팔레트는 반대쪽(-x)에 있어서 AGV 목적지는
  `palletX(로봇 x, 회전)`으로 계산하고, 상자가 날아가는 시작점은 팔레트의 세계 좌표(`localToWorld`)를 씁니다.
- **카드 겹침**: 로봇이 4대 이상이거나 화면이 700px보다 좁으면 정보 카드를 작게(이름·상태·온도만) 합니다.

**공장 건물과 벽 모니터** (`factory_env.js`): 로봇 뒤와 위를 채우는 배경입니다. 전부 기본 도형으로 만들었습니다.
- **구성**: 바닥(이음선, 통로 안전선), 뒷벽(아래 띠, 세로 홈, 창 4개), 노란 밑동의 철골 기둥, 천장 보와 길쭉한 조명판, 천장에서 바닥을 비추는 스포트라이트 3개와 하늘색 전체 빛. 천장은 내려다보는 기본 각도에서는 안 보이고 마우스로 위를 보면 나옵니다.
- **벽 모니터 3대**: ① 공장 현황(가동률, 생산량, 열린 알람 수, 통신 성공률, **최근 알람 3건**), ② 설비 상태(설비별 상태와 온도), ③ 온도 추이(설비별 선 그래프)와 출하·AGV 현황입니다. 값은 화면 위 지표 띠와 로봇들에서 받은 **실제 값**이고, 1초에 한 번만 `canvas`를 다시 그려 texture를 갱신합니다 (매 프레임 그리지 않으려고).
- **최근 알람 3건** (1번 모니터 아래쪽): 시각, 등급(P1 빨강, P2 노랑, P3 파랑), 설비, 알람 종류(서버 코드 `EQUIPMENT_FAULT` 등을 "설비 이상", "온도 경고", "통신 끊김", "카운터 초기화"로 바꿈), 확인 여부(미확인은 굵고 등급색, 확인됨은 흐리게)를 보여 줍니다. 가장 최근에 (다시) 발생한 순서로 고르고(`recentAlarms`), 같은 알람이 반복되면 "x2"처럼 횟수를 붙이고, 3건이 넘으면 "외 N건", 하나도 없으면 "열린 알람 없음"(초록)을 보여 줍니다. 서버가 1초마다 보내는 열린 알람 목록을 그대로 쓰는 실제 값입니다(화면 아래 알람 표와 같은 데이터이고 정렬만 다릅니다: 표는 등급 순, 벽은 최근 순).
- **계산 분리**: 상태별 개수(끊긴 설비는 '끊김'으로만 세어 이중 집계를 막음), 지표 단계 기준, 온도 이력 보관(`pushHistory`), 그래프 세로 범위와 점 좌표(`chartRange`, `chartPoints`)는 `factory_logic.js`에 있고 Node로 시험합니다. 그리는 코드는 눈으로 확인했습니다.
- **바닥 '반사'의 한계**: 바닥을 매끈하게(roughness를 낮춤) 해서 조명과 한 방향 빛이 번쩍이게 한 것이지, 거울처럼 로봇이 비치는 반사가 아닙니다. 진짜 반사는 Three.js의 추가 파일(`Reflector.js`, 내려받아야 함)이 필요하고 장면을 한 번 더 그려야 해서 아직 하지 않았습니다. 빛 번짐은 위 '빛 번짐' 항목에서 추가했습니다.
- **벽 위치**: 벽이 멀면 모니터 글자가 너무 작아져서, 뒤 줄 로봇 펜스 바로 뒤(z=-7)에 두고 카메라가 바라보는 점도 조금 올렸습니다. 뒤 줄 로봇의 정보 카드가 모니터 일부를 가리는 것은 알려진 한계입니다.

**빛 번짐(Bloom)** (`bloom.js`): 경광등, 천장 조명판, 모니터 테두리처럼 아주 밝은 부분이 주변으로 은은하게 번져 보이게 하는 **후처리** 효과입니다.
- **원리**: 장면을 바로 화면에 그리지 않고 한 번 거칩니다. (1) 장면을 메모리 위의 그림판에 그리고(`RenderPass`), (2) 그 그림에서 기준 밝기보다 밝은 부분만 골라 흐리게 퍼뜨려 원래 그림에 더하고(`UnrealBloomPass`), (3) 색을 화면용으로 되돌립니다(`OutputPass`).
- **직접 정한 값**: 세기 0.55, 퍼짐 0.5, 기준 밝기 1.15 (`BLOOM_SETTINGS`). 처음 0.8로 했더니 조명을 받은 노란 펜스까지 눈부시게 번져서, 스스로 빛나는 것(경광등 등)만 번지도록 기준을 높였습니다. 후처리 그림판은 기본적으로 계단 현상 방지(MSAA)가 꺼져 있어서 4배로 켰습니다.
- **외부 파일**: Three.js 공식 파일 10개(합계 30,247바이트)를 사용자의 허락을 받고 내려받아 `web/vendor/`에 넣었습니다. 지난번처럼 jsDelivr가 공개한 해시, unpkg 사본과 모두 대조했고, 파일끼리 불러오는 것이 전부 이 10개 안에 있는지, 외부로 접속하는 코드가 없는지도 확인했습니다. 크기와 해시는 `VENDOR.md`와 시험이 매번 확인합니다. 파일은 수정하지 않았습니다.
- **끌 수 있다**: 3D 화면 오른쪽 아래 스위치로 켜고 끕니다. 선택은 브라우저에 기억합니다(저장이 막혀도 동작). 그래픽이 약한 PC에서 느리면 끄면 됩니다. 파일을 불러오지 못하면 스위치는 "사용 불가"로 눌러지지 않고 나머지 화면은 그대로 동작합니다.
- **한계**: 화면을 한 번 더 처리하므로 그리는 양이 늘어납니다. 프레임 속도는 측정하지 못했습니다(브라우저 창이 가려지면 측정이 안 됩니다). 진짜 거울 반사는 아직 없습니다.

**상자 쌓기와 이동 로봇(AGV)** (`agv_logic.js`가 판단하고 `scene.js`가 그린다): 서버의 실제 값과 이어진 연출입니다.

```
로봇이 한 사이클을 끝냄 -> 서버의 '생산 카운트' +1 (설비 값)
   -> 그 로봇의 팔레트에 상자가 하나 쌓임 (위에서 떨어짐)         stackUpdate
   -> 4개가 차면 AGV를 부름                                         scene.js updateAgv
   -> AGV가 가장 가까운 가득 찬 팔레트로 이동 -> 상자가 하나씩 날아가 짐칸에 실림
   -> 출하장으로 이동 -> 상자를 내려놓음 (출하장 카드의 누적 수 증가) -> 대기 위치로 복귀
```

- **손에 든 상자**: 로봇 단계가 집기(2)~놓기(4)인 동안만 집게에 매달려 보입니다 (`isHolding`). 놓기가 끝나면 서버 카운트가 오르고, 그 순간 팔레트에 상자가 떨어져 쌓입니다.
- **AGV 상태**: 대기 -> 팔레트로 이동 -> 적재 중 -> 출하 운반 -> 하역 중 -> 복귀. 복귀 중에 새 요청이 생기면 대기 위치까지 가지 않고 바로 그쪽으로 갑니다. 요청이 여럿이면 가장 가까운 곳부터 하나씩 처리합니다.
- **왜 판단을 따로 뺐나?** `agvStep(상태, 시간, 요청들, ...)`은 이전 상태를 고치지 않고 새 상태와 이벤트("싣기 시작", "실었다", "내렸다")를 돌려주는 **순수 함수**입니다. 그래서 브라우저 없이 Node로 흐름 전체와 경계 상황(요청이 사라짐, 로봇 위치가 바뀜, 동시에 여러 팔레트가 참)을 시험할 수 있습니다. 도형을 움직이는 일은 `scene.js`가 결과를 받아서 합니다.
- **처음 값 처리**: 화면을 열 때 이미 쌓여 있던 생산 카운트는 한꺼번에 떨어뜨리지 않고 `카운트 % 4`개로 시작합니다. 카운트가 줄면(설비 재시작) 기준만 새로 잡습니다.
- **알아둘 점**: AGV는 서버가 읽는 장치가 **아닙니다** (Modbus 레지스터가 없음). 어떤 팔레트가 찼는지만 실제 생산 카운트에서 오고, AGV의 움직임 자체는 화면의 연출입니다. 팔레트가 찬 동안 더 쌓이는 상자는 화면에 그리지 않습니다.

**분위기와 깊이감**: 배경과 안개를 같은 어두운 색(`0x0d1117`)으로 맞추고, 18~42 떨어진 곳부터 서서히 어둠에 묻히게 했습니다
(`scene.fog`). 멀리 있는 것이 흐려지니 입체감이 생기고, 바닥 가장자리도 가려집니다. 로봇 셀 앞쪽 바닥에는 청록색으로 빛나는
점선(안내선)을 깔았습니다. 이동 로봇(AGV)이 이 선을 따라 다닙니다. 점선 조각 위치는 `robot_math.js`의
`dashXs`가, 길이는 `laneHalfLength`(로봇이 늘면 길어짐)가 정합니다.

**비스듬한 시점에서 카메라 거리**: 정면에서 볼 때의 계산만 쓰면, 옆에서 비스듬히 볼 때 가까운 쪽 로봇이 커 보여 화면 밖으로
잘립니다(실제로 처음에 ARM-03이 잘렸습니다). 그래서 카메라가 옆으로 비낀 각도로 가로 폭을 다시 계산하고
(`projectedHalfWidth`), 원근으로 커 보이는 만큼 20%의 여유(`PERSPECTIVE_MARGIN`)를 곱합니다.

**그림자**: 한 방향 빛(`sun`)만 그림자를 만듭니다. 바닥은 받기만(`receiveShadow`), 각 부품은 만들고 받습니다
(`castShadow`). 이렇게 하면 팔이 움직이는 대로 바닥의 그림자도 같이 움직여서 높이와 위치가 눈에 잘 들어옵니다.

## 5. 설계 결정과 이유

| 결정 | 이유 | 대안과 한계 |
|---|---|---|
| Modbus를 라이브러리 없이 직접 구현 | 패킷 구조, 바이트 처리, 오류 처리를 직접 다룬 경험을 보여 주려고 | 검증된 라이브러리(pymodbus)가 더 안전함. 직접 구현은 기능 코드 0x03 하나만 지원 |
| WebSocket도 직접 구현 | 표준 라이브러리에 없고, 내려받지 않아도 되며, 규격 이해를 보여 줄 수 있어서 | `websockets` 패키지가 더 안정적. 직접 구현은 조각난 메시지 등 일부를 지원하지 않음 |
| Python으로 전환 | 이 PC의 Windows 정책이 새로 빌드한 .NET 파일을 막아서 | C# WPF가 응용SW 공고(데스크톱, C#/C++)에는 더 가까움 |
| 설비마다 워커·연결 분리 | 장애 격리 | 설비가 수백 대면 연결 수 관리가 필요 |
| SQLite | 내려받을 것이 없고 이 규모에 충분 | 대량 시계열에는 InfluxDB 같은 전용 DB가 유리 |
| 알람 상태를 DB에 저장 | 수집 서버를 다시 켜도 열린 알람을 이어받음 | 알람이 많아지면 정리(보존 기간) 정책이 필요 |
| 웹은 127.0.0.1에만 열고 Host·Origin 검사 | 로컬 전용 도구라도 다른 웹사이트가 접근하는 것은 막아야 해서 | 외부 접속을 허용하려면 인증과 HTTPS가 필요 |
| 포트가 사용 중이면 시뮬레이터가 시작을 거부 | Windows는 같은 포트에 두 번째 서버가 오류 없이 붙을 수 있어서 (실제로 겪은 문제) | |
| Three.js 본체를 프로젝트에 보관(`web/vendor/`) | 외부 주소(CDN)에 의존하지 않아 오프라인에서도 동작하고, 해시로 변조를 확인할 수 있어서 | 라이브러리 업데이트를 직접 해야 함 |
| 3D 계산을 `robot_math.js`로 분리 | Three.js 없이 Node.js로 시험할 수 있고, 설명할 양도 줄어서 | 도형을 그리는 부분(`scene.js`)은 자동 시험이 어려워 브라우저에서 눈과 내부 값으로 확인 |
| 3D는 `import()`로 따로 불러오고 실패하면 안내 | 그래픽 가속이 없는 브라우저에서도 카드와 알람 표는 동작해야 해서 | |
| 3D는 기본 도형 조립 (모델링 안 함) | 설명할 수 있는 크기로 만들기 위해, 그리고 이 프로젝트의 초점은 데이터 흐름이라서 | 외형이 소박함. 3D 애니메이터 공고(Blender 모델링)와는 다른 경험 |

## 6. 면접 질문과 답변 포인트

### 프로젝트 전반
1. **어떤 프로젝트인가요?** 가상 로봇 6대의 데이터를 Modbus TCP로 동시에 수집하고, SQLite에 저장하고, 알람을 판정하고, 웹으로 실시간 전송하는 설비 모니터링 시스템입니다. 실제 설비는 없어서 가상 로봇으로 만들었고, 통신 안정성과 장애 격리가 핵심입니다.
2. **왜 이 주제를 골랐나요?** 제조 현장의 설비 데이터 수집은 스마트팩토리와 제조 IT의 기본이라, 공고가 요구하는 소켓 통신, 재접속, 시계열 저장을 직접 구현해서 보여 주려고 했습니다.
3. **혼자 만들었나요? AI를 썼나요?** AI 코딩 도구와 함께 구현했고, 설계 결정과 검증은 직접 했다고 말하세요. 시험 136개를 만들었고, 시험이 정말 오류를 잡는지 코드를 일부러 망가뜨려 확인했습니다 (변이 시험). 어느 부분을 직접 이해하고 설명할 수 있는지가 중요하니, 이 문서의 2번과 3번을 먼저 익히세요.
4. **가장 어려웠던 점은?** 후보: 이 PC의 보안 정책이 .NET 빌드를 막아서 Python으로 바꾼 일, 윈도우에서 같은 포트에 서버가 두 개 붙어 시험 결과가 오염된 일(포트 사용 중이면 시작을 거부하게 고침).

### 통신
5. **Modbus TCP 프레임 구조를 설명해 보세요.** MBAP 헤더 7바이트(트랜잭션 번호 2, 프로토콜 ID 2, 길이 2, 유닛 ID 1) + PDU(기능 코드, 주소, 개수). 위 2번 항목의 그림을 그리면 됩니다.
6. **트랜잭션 번호는 왜 있나요?** 요청과 응답을 짝지으려고요. 응답의 번호가 요청과 다르면 규격 위반으로 처리하고 연결을 닫습니다.
7. **응답이 짧게 오거나 깨지면?** `readexactly`로 필요한 바이트 수만큼 읽고, 헤더의 프로토콜 ID, 길이 범위, 바이트 수 필드를 검사합니다. 어긋나면 `ModbusProtocolError`로 연결을 닫고 재접속합니다.
8. **TCP는 스트림인데 메시지 경계는 어떻게 구분하나요?** 헤더의 길이 필드로 PDU 길이를 알아내서 그만큼만 읽습니다.
9. **시간 초과는 어떻게 처리하나요?** `asyncio.timeout`으로 요청마다 제한 시간(1초)을 둡니다. 넘으면 연결을 닫습니다 (늦게 온 응답이 다음 요청과 섞이는 것 방지).

### 안정성
10. **연결이 끊기면 어떻게 하나요?** 연결을 닫고 1, 2, 4초(최대)로 늘려 가며 재접속합니다. 읽기에 성공하면 1초로 돌아갑니다.
11. **왜 대기 시간을 늘리나요?** 꺼진 설비에 계속 접속을 시도하는 낭비와 부담을 줄이면서, 설비가 돌아오면 최대 4초 안에 다시 붙게 하려고요.
12. **한 설비가 끊기면 다른 설비는?** 영향 없습니다. 설비마다 워커와 연결과 상태가 따로입니다. 3대 중 1대만 껐다 켜는 시험과 실측으로 확인했습니다 (나머지는 실패 0).
13. **멀티스레드를 썼나요?** 비동기(asyncio)로 한 스레드에서 번갈아 처리합니다. (공고의 "멀티스레드·비동기 경험"에 비동기 쪽으로 답하세요. 시뮬레이터 서버 쪽은 스레드를 썼으니 그 차이도 설명할 수 있어야 합니다.)
14. **끊긴 설비의 마지막 값은 어떻게 보여 주나요?** 현재 값처럼 보이지 않게 흐리게 하고 "마지막 수신 N초 전 (값은 오래됨)"을 표시합니다. 오래된 값을 정상 값으로 오해하면 위험하기 때문입니다.

### 알람과 데이터
15. **알람 채터링을 어떻게 줄였나요?** 해제 지연 3초(조건이 3초 동안 계속 사라져야 해제)와 반복 묶기 60초(해제 후 60초 안의 재발생은 기존 알람을 다시 열고 횟수만 올림). 같은 조건에서 27줄이 6줄이 됐고 발생 횟수 합은 같았습니다.
16. **이미 확인한 알람이 다시 발생하면?** 새 알람으로 만듭니다. 확인한 사람이 재발생을 놓치면 안 되기 때문입니다.
17. **확인(ACK)과 해제는 왜 따로인가요?** 값이 정상으로 돌아와도 사람이 문제를 봤다는 기록이 필요해서요. 해제됐지만 미확인인 알람은 목록에 남습니다.
18. **설비가 재시작해서 생산 카운트가 0으로 돌아가면 생산량은?** `count_delta`가 줄어든 값을 "재시작 후 센 개수"로 더하고, 65536에서 0으로 한 바퀴 도는 경우와 구분합니다. 알람(COUNTER_RESET)도 하나 남깁니다.
19. **왜 SQLite인가요? 시계열 DB는?** 이 규모(설비 3대, 초당 6건)에 충분하고 내려받을 것이 없어서입니다. 데이터가 커지면 InfluxDB 같은 시계열 DB로 바꿀 수 있게 저장 부분을 분리해 뒀다고 설명하되, 실제로 InfluxDB를 써 본 것은 아니라고 정직하게 말하세요.
20. **수집 서버를 다시 켜면 알람은?** 알람 상태가 DB에 있어서 열린 알람을 이어받습니다. 시험(`test_new_manager_takes_over_open_alarms`)으로 확인했습니다.

### 웹
21. **실시간 전송은 어떻게 하나요?** WebSocket으로 서버가 값이 생길 때마다 밀어 줍니다. 접속할 때와 1초마다 전체 상태(`state`)를 다시 보내서, 개별 메시지를 놓친 화면도 곧 맞는 상태가 됩니다.
22. **WebSocket을 직접 구현했다던데?** 핸드셰이크(키에 고정 문자열을 붙여 SHA-1, Base64), 프레임 인코딩(길이 125 이하/65535 이하/그 이상으로 길이 표현이 달라짐), 클라이언트 프레임 마스킹 해제를 직접 했습니다. 규격서(RFC 6455)의 공식 예제 값으로 시험했습니다. 다만 조각난 메시지는 지원하지 않습니다.
23. **느린 브라우저가 있으면 수집이 느려지지 않나요?** 접속자마다 크기가 정해진 대기열을 두고 가득 차면 오래된 메시지부터 버리며, 5초 안에 못 보내면 그 접속을 끊습니다. `publish`는 기다리지 않아서 수집을 붙잡지 않습니다.
24. **보안은 어떻게 신경 썼나요?** 로컬(127.0.0.1)에만 열고, Host 헤더가 로컬이 아니면 거절(DNS 리바인딩 방지), WebSocket은 Origin이 같은 주소일 때만 허용(다른 사이트가 몰래 접속하는 것 방지), 정적 파일은 폴더 밖으로 못 나가게 막았습니다. 외부에 공개하려면 인증과 HTTPS가 더 필요합니다.

### 시험
25. **어떻게 검증했나요?** 자동 시험 Python 308개 + JS 76개: 프레임 검사, 재접속, 장애 격리, 알람 규칙, 저장, WebSocket 규격, 보안 규칙, 패킷 해석, 지표 계산, 조회·명령 입력 검사. 거기에 실제로 로봇 3대를 띄워 한 대만 껐다 켜고, 브라우저로 화면까지 확인했습니다.
26. **시험이 정말 잘 만들어졌는지는요?** 코드를 일부러 망가뜨려서(보안 검사 끄기, 길이 경계 틀리게 등) 시험이 잡아내는지 확인했습니다. 한 번은 시험이 못 잡는 빈틈(길이 경계값)을 발견해서 시험을 보강했습니다.

### 3D 화면 (Three.js)
27. **3D는 어떻게 만들었나요?** Three.js로 원기둥, 상자, 구 같은 기본 도형을 이어 붙여 로봇 팔을 만들었습니다. 장면(Scene), 카메라, 렌더러, 물체(Mesh), 매 프레임 반복하는 애니메이션 루프, 이 다섯 가지로 구성됩니다. Three.js는 이 프로젝트에서 처음 써 봤습니다.
28. **로봇 팔은 어떻게 움직이나요?** 부모-자식 구조입니다. 어깨 그룹 안에 기둥과 팔꿈치 그룹이 들어 있고, 팔꿈치 그룹 안에 팔과 집게가 있어서, 어깨 그룹의 회전값 하나만 바꾸면 아래 부품이 모두 같이 돕니다. 서버가 보낸 관절 각도를 라디안으로 바꿔 어깨(y축)와 팔꿈치(z축) 회전값에 넣습니다.
29. **서버 값을 바로 적용하지 않고 왜 따라가게 했나요?** 서버는 0.5초마다 값을 보내고 화면은 1초에 약 60번 그려서, 그대로 적용하면 뚝뚝 끊깁니다. 값은 '목표'로 기억하고 화면의 '현재' 값이 매 프레임 그쪽으로 조금씩 다가가게 했습니다.
30. **컴퓨터 성능이 달라도 같은 속도로 움직이나요?** 네. 지난 프레임 이후 흐른 시간(dt)을 반영한 지수 감쇠를 씁니다. 이 식은 프레임을 쪼개서 여러 번 적용해도 한 번 적용한 것과 결과가 같아서, 프레임 속도와 무관합니다. 시험으로 확인했습니다.
31. **통신이 끊기면 3D는 어떻게 되나요?** 그 로봇은 회색으로 바뀌고 마지막 자세 그대로 멈추며 컨베이어 상자도 멈춥니다. 정보 카드는 "끊김"으로 바뀌고 "통신 끊김 · 값은 오래됨"이 표시됩니다. 다른 로봇은 영향 없이 계속 움직입니다.
32. **3D를 못 쓰는 브라우저에서는요?** 3D는 `import()`로 따로 불러오고 실패하면 안내만 보여 줍니다. 카드와 알람 표는 계속 동작합니다. 3D 파일을 뺀 복사본으로 실제 브라우저에서 확인했습니다.
33. **Three.js 파일은 어떻게 관리했나요?** 인터넷에서 받은 파일을 `web/vendor/`에 그대로 보관했고(수정하지 않음), 출처, 버전, 라이선스(MIT)를 `VENDOR.md`에 적었습니다. 받을 때 jsDelivr가 공개한 해시와 다른 미러(unpkg)로 두 번 확인했고, 시험이 매번 해시를 비교해서 파일이 바뀌면 실패합니다. 외부 주소에 의존하지 않아 오프라인에서도 동작합니다.
34. **3D는 어떻게 시험했나요?** 계산 부분(각도 변환, 따라가기, 색, 배치, 경광등, 롤러, 안내선, 비스듬한 시점의 폭, 3D 위치→화면 위치)을 `robot_math.js`로 분리해서 Node.js로 25개를 시험했고, 파일 연결과 무결성도 자동으로 확인합니다. 실제로 그려진 모양은 자동 시험이 어려워서 브라우저에서 눈으로 보고, 화면의 카드 값과 3D 로봇의 내부 값이 같은지 숫자로 비교했습니다. 이 한계를 알고 있다고 말하세요.
35. **3D 모델링을 했나요?** 아니요. 기본 도형을 조립했습니다. Blender 같은 모델링이나 애니메이션 제작은 하지 않았고, 이 프로젝트의 초점은 설비 데이터가 실시간으로 화면에 반영되는 흐름입니다.

### 한계 (먼저 말하는 편이 신뢰를 줍니다)
36. **실제 설비와 연동해 봤나요?** 아니요. 가상 로봇(시뮬레이터)으로 만들었고, 로봇 동작은 정해진 순서대로 만든 값입니다. 실제 PLC 연동은 해 보지 않았습니다.
37. **무엇이 부족한가요?** 기능 코드 0x03만 지원하고(쓰기, OPC UA 등은 없음), 인증이 없고, 단일 프로세스이며, SQLite라 대량 데이터에는 한계가 있고, 3D는 기본 도형 조립이라 외형이 소박합니다. C/C++, Qt, 임베디드 경험은 이 프로젝트로 채우지 못합니다.

### 패킷·지표·명령 (화면용 서버 기능)
38. **패킷 뷰어는 왜 만들었나요?** 통신을 직접 구현했으니 "실제로 어떤 바이트가 오가는지"를 화면에서 보여 주려고요. 요청 12바이트, 응답 29바이트를 필드별(헤더, 기능 코드, 주소, 레지스터 값)로 색을 나눠 설명합니다. 해석은 서버에서 한 번만 하고 시험이 있습니다.
39. **실패한 패킷은 어떻게 보나요?** 마지막 정상 교환과 마지막 실패 교환을 따로 저장합니다. 실패 직후 정상 응답이 와도 실패한 바이트가 덮어써지지 않습니다. 깨진 응답은 가능한 만큼 해석하고 어디서 규격과 어긋나는지(`error` 필드) 표시합니다.
40. **가동률은 어떻게 계산했나요?** 이상(정지)이 아닌 상태로 읽은 표본 수를 읽었어야 할 표본 수로 나눕니다. 통신이 끊겨 못 읽은 시간은 가동 안 한 것으로 세고, 설비의 첫 표본 이전은 세지 않습니다. 표본이 예상보다 촘촘히 쌓여도 100%를 넘지 않게 제한했고, 경계 조건을 시험했습니다. 표본 기반 근사치이고 OEE 같은 정식 지표는 아닙니다.
41. **알람 확인 명령 보안은요?** 입력은 모두 믿지 않습니다: 크기 4096바이트, 이름 길이와 제어문자, id 타입(`True` 거절), 속도 제한(5초에 20개, 초과하면 1008로 끊음). 오류 내용은 로그에만 남기고 화면에는 일반 문구만 보냅니다. 인증은 없어서 로컬 전용이라는 전제입니다.
42. **시험에서 실제로 버그를 잡은 적이 있나요?** 네. 패킷 해석이 레지스터 이름을 주소가 아닌 순서로 붙이던 것, 솎아내기가 최대 개수를 넘을 수 있던 것, 숫자 검사가 아랍 숫자를 통과시키던 것을 시험이 잡아서 고쳤습니다. 새 코드를 일부러 망가뜨린 17가지 변이도 모두 시험이 잡았습니다.
43. **AGV는 실제 데이터인가요?** 아닙니다. 서버가 읽는 장치는 로봇 팔 6대뿐이고 AGV는 화면의 연출입니다. 다만 "언제 부르는가"는 실제 값에서 옵니다. 로봇의 생산 카운트가 늘 때마다 팔레트에 상자가 쌓이고 4개가 차면 AGV가 출동합니다. 실제 설비에서는 AGV도 자체 통신 값을 가진 설비로 수집기에 추가하면 됩니다.
44. **AGV 로직은 왜 따로 파일로 뺐나요?** 판단(언제 어디로 가는가)과 그리기(도형을 움직이는가)를 나누려고 했습니다. 판단은 입력을 받아 새 상태를 돌려주는 순수 함수라 Node로 흐름 전체를 시험할 수 있고(시험 19개), 시험이 진짜 틀린 코드를 잡는지는 일부러 코드를 망가뜨려 확인했습니다(12곳 모두 잡음, 약했던 시험 1개는 강화).
45. **로봇 모양이 두 가지인데 서버가 알려 주나요?** 아닙니다. 서버는 모양을 모르고 모두 같은 3가지 값만 보냅니다. 화면이 설비 이름 끝 번호의 홀짝으로 모양을 정합니다. 실제 현장이라면 설비 종류를 설정(예: 수집기의 설비 목록 항목)으로 받게 확장하면 됩니다.
46. **스카라는 어떻게 관절 팔과 같은 위치에 닿나요?** 역운동학을 직접 계산했습니다. 팔 끝이 가야 할 점(방향과 수평 거리)을 구하고, 마디 두 개의 길이로 코사인 법칙을 써서 팔꿈치 각도를, 아크탄젠트로 첫째 마디 방향을 구합니다. 반대로 그 각도에서 팔 끝을 다시 계산해 목표와 일치하는지 시험으로 확인했습니다. 외부 라이브러리는 쓰지 않았습니다.
47. **3D 공장 벽의 모니터는 진짜 데이터인가요?** 네. 화면 위 지표 띠와 로봇들이 받은 실제 수집값(가동률, 생산량, 알람 수와 최근 알람 3건, 설비별 상태와 온도)을 같은 서버 값에서 가져와 1초에 한 번 `canvas`에 다시 그려 3D 판에 입힙니다. 가짜 숫자가 아닙니다. 다만 모니터는 화면에 걸린 장식이고, 서버가 읽는 장치는 아닙니다.
48. **3D 배경은 어떻게 만들었고 한계는요?** 기본 도형(상자, 원기둥)만 조합했고 외부 모델은 쓰지 않았습니다. 사진 같은 질감과 거울 반사는 없고, 바닥은 윤만 낸 정도입니다. 빛 번짐은 Three.js 공식 후처리 파일 10개를 사용자의 허락을 받고 내려받아 해시로 검증해서 넣었다고 설명하세요. 더 가까이 가려면 거울 반사 파일이 더 필요합니다.
49. **빛 번짐을 넣을 때 외부 파일은 어떻게 다뤘나요?** 먼저 필요한 파일 10개의 이름, 출처, 크기를 사용자에게 알리고 허락을 받은 뒤 내려받았습니다. 새 폴더에 받아서 jsDelivr가 공개한 해시, unpkg 사본과 모두 대조하고, 파일끼리 불러오는 것이 전부 이 안에 있는지, 외부 접속 코드가 없는지 확인했습니다. 그다음 `web/vendor/`에 수정 없이 넣고 크기와 해시를 시험에 기록해 한 바이트라도 바뀌면 시험이 실패하게 했습니다. 불러오기에 실패해도 빛 번짐만 빠지게 `import().catch`로 격리했고, 느린 PC를 위해 끌 수 있는 스위치를 뒀습니다.
50. **통신 장애는 어떻게 시험했나요?** 실제 가상 설비 프로세스 3대와 진짜 수집기를 시나리오마다 새로 띄우고, 1번 설비에만 장애(응답 지연 300ms, 시간 초과를 일으키는 지연 1500ms, 7번째마다 연결 끊김, 7번째마다 깨진 응답, 전원 꺼짐과 8초 뒤 복구)를 줬습니다. 결과는 수집기가 저장한 DB의 측정값 시각, 이벤트, 알람으로 계산했습니다. 모든 시나리오에서 정상 설비는 기준과 같은 속도로 계속 수집해 장애가 번지지 않았고, 전원이 꺼지면 0.2~0.3초 만에 알아채고 약 5초 뒤 통신 끊김 알람이 났습니다. 자세한 표는 `docs/COMM_TEST.md`입니다.
51. **측정으로 알게 된 약점은 무엇인가요? 어떻게 고쳤나요?** 처음 측정에서 네 가지를 찾았고 모두 고친 뒤 같은 방법으로 다시 쟀습니다. (1) 수집 주기가 `응답 시간 + 0.5초`라서 설비가 느리면 주기가 늘어났습니다(지연 300ms에서 초당 2개 -> 1.2개). **고정 주기**(다음 읽을 시각을 정해 두고 그때까지만 쉼)로 바꿔 초당 2.00개를 유지합니다. (2) 재접속 대기 상한 때문에 복구가 최대 8초 늦었습니다. 상한을 **4초**로 줄여 최악의 복구가 7.8초에서 3.9초가 됐습니다. (3) 웹 방송 메시지가 설비 수에 비례해 커서(100대에서 1초마다 260KB) 패킷 기록을 방송에서 빼고 고른 설비 하나만 `/api/packet`으로 가져가게 해 **43KB**가 됐습니다. (4) 오래된 측정값을 지우는 정책이 없어서 **7일이 지나면 자동 삭제**(알람은 보존)를 넣었습니다. 측정하기 전에는 몰랐던 것들이고, 고친 뒤 다시 재서 효과를 확인했습니다. 고치고도 남은 한계(메시지가 여전히 설비 수에 비례, 보관 정책을 7일 동안 실제로 돌려 보지는 못함)는 문서에 적었습니다.
52. **30대를 동시에 수집하면 어떤가요?** 수집기 CPU 평균 2.8%(한 코어 기준), 메모리 28MB, 수집 간격 최대 0.55초, 누락 0건이었습니다(개선 전에는 CPU 1.8%, 메모리 30MB). 여유가 커서 6, 60, 100대도 재 봤고 100대에서도 CPU 4.6%, 메모리 34MB, 간격 최대 0.54초였습니다. 설비마다 스레드가 아니라 asyncio 작업 하나를 돌리는 구조라서 메모리와 CPU가 거의 늘지 않습니다. 다만 같은 PC의 루프백 통신, 접속자 1명, 짧은 시간에서 잰 값이므로 실제 현장의 보장은 아니라고 말하세요.
53. **측정 도구를 어떻게 믿을 수 있나요?** CPU와 메모리는 윈도우 API(`GetProcessTimes`, `GetProcessMemoryInfo`)로 직접 읽었고, 수집이 빠졌는지는 수집기가 스스로 센 숫자가 아니라 DB에 저장된 측정값의 시각으로 계산했습니다. 통계 계산과 WebSocket 프레임 해석은 시험 10개로 확인하고, 계산을 일부러 망가뜨린 8곳을 모두 잡았습니다. 도구를 만들다 시나리오 사이에 포트가 남아 있어 한 번 실패한 일이 있어서, 이전 프로세스가 완전히 끝나기를 기다리도록 고쳤습니다.
54. **고정 주기 폴링은 어떻게 만들었고 주의할 점은?** 읽기를 시작하며 `다음에 읽을 시각`을 정해 두고(`next_schedule`), 읽기가 끝나면 그 시각까지만 쉽니다. 응답이 느려도 주기가 늘지 않습니다. 주의할 점은 응답이 주기보다 길 때입니다. 밀린 읽기를 몰아서 하면 이미 느린 설비에 요청이 쏟아지므로, 일정을 놓치면 지금을 새 기준으로 삼고 몰아서 읽지 않습니다. 또 100대가 같은 순간에 읽고 저장하면 몰리므로 설비마다 시작을 한 주기 안에 고르게 엇갈립니다(`stagger_delay`). 재접속하면 일정을 새로 시작합니다. 시험 13개가 확인하고, 옛 방식으로 되돌린 코드를 포함해 일부러 망가뜨린 6가지를 모두 잡습니다.
55. **보관 정책은 어떻게 동작하나요?** 기본 7일(`--retention-days`, 0이면 끔)이 지난 측정값과 통신 이벤트를 시작할 때 한 번, 그다음 1시간마다 지웁니다. 알람은 건수가 적고 확인 기록이라 지우지 않습니다. 설비마다 5,000건씩 덩어리로 지우고 사이사이 쉬어서 오래 쌓인 DB를 처음 정리할 때도 수집이 멈추지 않으며, 정리가 실패해도 수집은 계속됩니다. 단위 시험 12개(경계, 덩어리, 알람 보존, 오류에도 계속 동작)로 확인했고 일부러 망가뜨린 12가지를 모두 잡았습니다. 다만 7일을 실제로 돌려 보지는 못했다고 말하세요.
56. **웹 방송에서 패킷 기록을 왜 뺐나요?** 부하 시험에서 `state` 메시지가 설비 수에 비례해 커지는 것을 찾았습니다(설비당 2.6KB, 100대에서 260KB). 원인은 설비마다 패킷 기록을 통째로 1초마다 모든 접속자에게 보내던 것이었습니다. 패킷 뷰어는 한 번에 설비 하나만 보여 주므로, 방송에서 빼고 고른 설비만 `/api/packet?device=`로 가져옵니다(1초마다, 요청이 겹치지 않게 하고 설비를 바꾸면 이전 응답은 버림). 설비당 0.43KB로 줄어 100대에서 43KB가 됐습니다. 이 주소도 설비 이름을 목록에서 확인하고 모르는 이름은 404로 거절합니다.

## 7. 직접 해 보며 이해하기

터미널에서 `factory-twin` 폴더로 이동한 뒤 합니다. 각 실습은 5분 안팎입니다.

## 8. 한계와 알려진 문제

- 실제 설비가 아니라 시뮬레이터입니다. 로봇 동작은 정해진 순서로 만든 값입니다.
- 3D는 기본 도형을 조립한 외형입니다. 모델링은 하지 않았고, 그림자는 있지만 충돌 같은 물리 표현은 없습니다. 바닥은 윤이 날 뿐 거울 반사는 아닙니다. 빛 번짐은 있지만 그리는 양이 늘어나 약한 PC에서는 느려질 수 있어 끌 수 있게 했습니다. 그림자와
  빛 때문에 그리는 양이 늘었으므로, 성능이 낮은 PC에서는 느려질 수 있습니다 (프레임 속도는 측정하지 못했습니다).
- 3D 로봇이 그려진 모양 자체는 자동 시험으로 확인할 수 없습니다. 계산 부분(`robot_math.js`)은 자동 시험이 있고,
  그려진 모양은 브라우저에서 눈과 내부 값으로 확인했습니다.
- 로봇의 사이클(집기, 놓기)은 서버가 보낸 관절 값을 따라 움직이는 것이고, 화면에서 상자를 실제로 집어 옮기는 물리
  동작은 아닙니다. 컨베이어 위 상자는 속도 값대로 흐르는 장식이며 실제 상자 위치와 연결되어 있지 않습니다. 팔레트에 쌓이는 상자는 생산 카운트와 이어져 있지만, AGV의 움직임은 서버가 읽는 값이 아닌 화면의 연출입니다.
- 통신 시험과 부하 시험은 같은 PC의 루프백 통신에서 접속자 1명, 짧은 시간(20~60초)으로 쟀습니다. 실제 네트워크 손실과 지연 변동, 장시간 안정성은 측정하지 못했습니다. 처음 측정에서 찾은 약점 네 가지(주기가 응답 시간만큼 늘어남, 복구 최대 8초, 웹 메시지가 큼, 보관 정책 없음)는 고쳤습니다. 남은 한계: 복구는 최대 4초 늦을 수 있고, 웹 `state` 메시지는 여전히 설비 수에 비례해 커지며(100대 43KB, 바뀐 값만 보내는 방식은 안 만듦), 보관 정책은 단위 시험으로만 확인하고 7일 동안 실제로 돌려 보지 못했으며, 오래된 값을 요약해 남기는 다운샘플 저장은 없습니다 (`docs/COMM_TEST.md`).
- 로봇 모양(관절 팔/스카라)은 서버 값이 아니라 설비 이름 끝 번호의 홀짝으로 화면이 정합니다. 줄은 최대 두 줄까지 만들었고, 로봇이 많이 늘면(예: 30대) 한 줄의 길이가 길어져 화면에서 작게 보입니다.
- 통신 이벤트 목록은 화면을 연 **이후**의 이벤트만 보여 줍니다 (접속 직전 이벤트는 목록에 없음).
- 알람 확인(ACK)은 지금 터미널 도구로만 할 수 있습니다. 화면에서 누르는 기능은 6단계에서 추가합니다.
  그래서 터미널에서 확인한 알람은 화면 표에 최대 1초 안에 반영됩니다 (`state` 메시지가 1초마다 가기 때문).
- Modbus 기능 코드 0x03만 지원합니다. WebSocket은 조각난 메시지를 지원하지 않습니다.
- 인증이 없어서 로컬 전용으로만 열어야 합니다.

## 9. 용어집

| 용어 | 뜻 |
|---|---|
| PLC | 공장 설비를 제어하는 작은 컴퓨터 (프로그래머블 로직 컨트롤러) |
| 레지스터 | PLC가 값을 담아 두는 번호 붙은 칸. 이 프로젝트에서는 한 칸이 0~65535 숫자 하나 |
| MBAP 헤더 | Modbus TCP 메시지 앞의 7바이트 머리 |
| PDU | 기능 코드와 데이터 부분 |
| 폴링 | 일정 간격으로 계속 물어서 값을 읽어 오는 방식 |
| 백오프 | 실패할 때마다 재시도 간격을 늘리는 것 |
| 장애 격리 | 한 부분의 고장이 다른 부분으로 번지지 않게 하는 설계 |
| 채터링 | 기준선 근처에서 상태가 계속 바뀌는 현상 |
| 히스테리시스 | 올라갈 때와 내려갈 때 기준을 다르게 해서 경계에서 흔들리지 않게 하는 것 |
| ACK | 알람을 사람이 확인했다는 표시 (acknowledge) |
| 디지털 트윈 | 실제 설비의 상태를 따라 움직이는 가상 모형 |
| MES | 생산 현장을 관리하는 시스템 (제조 실행 시스템) |
| WAL | SQLite가 쓰기를 먼저 기록해 두는 안전 장치 |
| 변이 시험 | 코드를 일부러 망가뜨려서 시험이 잡아내는지 확인하는 방법 |
