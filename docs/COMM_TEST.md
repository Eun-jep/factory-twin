# 통신 시험과 부하 시험 결과 (7단계)

수집 서버가 통신 장애를 만났을 때 실제로 어떻게 동작하는지, 설비가 많아져도 버티는지를 **실제 프로세스로 돌려서 잰** 기록입니다.
같은 방법으로 **두 번** 쟀습니다. 처음 측정(2026-11-17)에서 약점 4가지를 찾았고, 그것을 고친 뒤(2026-11-18) 다시 재서
**개선 전과 후를 나란히** 적었습니다. 다시 재현하는 방법은 맨 아래에 있습니다.

## 한눈에 보기

| 질문 | 개선 전 (처음 측정) | 개선 후 (다시 측정) |
|---|---|---|
| 한 설비의 통신이 나빠지면 다른 설비도 영향을 받나? | 받지 않음 (정상 설비 초당 1.95개) | **받지 않음** (정상 설비 초당 2.00개) |
| 응답이 느리면 (지연 300ms) | 수집이 **초당 2개 -> 1.2개**로 줄어듦 | **초당 2.00개 유지** |
| 설비가 다시 켜진 뒤 값이 돌아오기까지 (최악) | 최대 **약 8초** (실측 7.8초) | 최대 **약 4초** (실측 3.9초) |
| 설비 30대 동시 수집 | CPU 1.8%, 메모리 30MB, 누락 0 | CPU 2.8%, 메모리 28MB, 누락 0 |
| 웹 방송 `state` 메시지 (100대) | 1초마다 **260KB** | 1초마다 **43KB** (약 6분의 1) |
| 오래된 측정값 | 쌓이기만 함 (하루 6대 110MB ~ 100대 1.9GB) | **7일이 지나면 자동 삭제** (알람은 보존) |
| 설비 전원이 꺼지면 알아채는 시간 | 0.3초 | 0.2초 (그대로) |

## 1. 통신 장애 시나리오

### 방법
- 가상 설비 프로세스(`simulator/modbus_sim.py`) 3대와 **진짜 수집기**(`python -m collector`)를 시나리오마다 새로 띄웁니다.
- **1번 설비(ARM-01)에만** 장애를 주입하고 2·3번은 정상으로 둬서, 장애가 다른 설비로 번지는지도 같이 봅니다.
- 장애 주입은 시뮬레이터 옵션입니다: `--delay-ms`(응답 지연), `--drop-every`(N번째 요청에 응답 없이 연결 끊기), `--garbage-every`(N번째 요청에 깨진 응답).
- 결과는 수집기가 저장한 DB(측정값, 이벤트, 알람)에서 읽습니다. 수집기 설정은 기본값(폴링 0.5초, 응답 제한 1.0초)입니다.
- 도구: `tools/comm_scenarios.py` (포트 7101~7103과 임시 DB만 사용)

### 결과: 개선 전 -> 개선 후

| 시나리오 | 1번 설비 (장애 주입) 개선 전 | 1번 설비 개선 후 | 2·3번 설비 (정상) | 알람 |
|---|---|---|---|---|
| 정상 (기준) | 초당 1.95개, 간격 0.507초 | 초당 **2.00개**, 간격 0.500초 | 개선 전 1.95 -> 후 2.00개, 최대 공백 0.52초 | 없음 |
| 응답 지연 300ms | 초당 **1.20개**, 간격 0.81초 | 초당 **2.00개**, 간격 0.500초 | 초당 2.00개 | 없음 |
| 응답 지연 1500ms (제한 1.0초 초과) | 0개 (모두 시간 초과) | 0개 (같음) | 초당 2.00개 | 통신 끊김 P1, +3.2초 (같음) |
| 7번째 요청마다 연결 끊김 | 초당 1.44개, 최대 공백 1.5초 | 초당 1.44개, 최대 공백 1.53초 (같음) | 초당 2.00개 | 없음 |
| 7번째 요청마다 깨진 응답 | 초당 1.44개, 최대 공백 1.5초 | 초당 1.44개, 최대 공백 1.51초 (같음) | 초당 2.00개 | 없음 |
| 전원 꺼짐 -> 8초 뒤 켜짐 | 최대 공백 9.6초, 끊김 인지 0.3초, 복구 1.0초 | 최대 공백 9.5초, 인지 0.2초, 복구 0.8초 | 초당 2.00개 | 통신 끊김 P1, +13.2초 발생, +17.2초 해제 |

- 정상 설비의 초당 1.95개가 2.00개가 된 것도 고정 주기의 효과입니다(주기가 읽기 시간만큼 늘어나지 않으므로).
- 1500ms 지연 시나리오의 접속 이벤트가 늘어난(접속 3 -> 5, 읽기 실패 4 -> 6) 것은 재접속 대기 상한이 짧아져 같은 시간에 시도가 더 많아졌기 때문으로 보입니다.
- 전원 꺼짐(8초)의 복구 0.8초는 켠 시각이 마침 재접속 시도 시점과 가까워서 짧게 나온 값입니다. 최악의 경우는 아래 표로 봅니다.

### 재접속 대기 상한 8초 -> 4초: 복구가 얼마나 빨라졌나

설비가 꺼져 있던 시간을 바꿔 가며, **다시 켠 뒤 값이 돌아오기까지** 걸린 시간을 쟀습니다. 수집기 옵션 `--backoff-max`로 상한만 8초와 4초로 바꾸고 나머지는 같은 코드입니다.

| 꺼져 있던 시간 | 상한 8초 (개선 전) | 상한 4초 (개선 후) | 가장 긴 수집 공백 (8초 -> 4초) |
|---|---|---|---|
| 9초 | 0.2초 | 0.3초 | 10.0초 -> 10.1초 |
| 10초 | **7.8초** | **3.9초** | 18.6초 -> 14.6초 |
| 11초 | **6.9초** | **2.8초** | 18.6초 -> 14.5초 |

- 재접속 시도는 꺼진 직후부터 1초, 2초, 4초, (8초) 간격으로 일어나서, 켜진 직후에 막 시도를 놓친 경우가 최악입니다. 그 최악이 상한과 같아집니다(8초 -> 4초). 9초일 때는 두 방식 모두 우연히 켜진 직후에 시도가 있어서 차이가 없습니다.
- 바꿔도 되는 이유: 상한을 줄이면 꺼진 설비에 접속을 시도하는 횟수는 늘지만, 4초에 한 번은 설비와 서버 모두에게 부담이 아닙니다.

### 해석 (무엇이 의도대로이고 무엇이 한계인가)

**의도대로 동작한 것**
1. **장애 격리**: 설비마다 워커, 연결, 상태가 따로라서 어떤 장애에서도 정상 설비의 수집이 달라지지 않았습니다.
2. **깜빡이는 통신과 끊긴 통신의 구분**: 7번째마다 끊기는 경우는 곧바로 재접속해 복구되고 연속 실패가 1회뿐이라 알람을 울리지 않습니다. 연속 3회 실패해야 통신 끊김 P1 알람이 발생합니다(`comm_lost_after = 3`). 불안정한 통신 때문에 알람이 계속 울리는 것을 막기 위한 설계입니다.
3. **재접속 대기를 늘려 가며 재시도**: 1초, 2초, 4초(최대)로 늘리고, 읽기에 한 번 성공하면 1초로 돌아갑니다. 꺼진 설비에 요청이 몰리지 않습니다.
4. **이상한 응답은 연결을 닫고 처음부터**: 깨진 응답(프로토콜 ID가 틀린 헤더)도 시간 초과도 연결 상태를 믿을 수 없다고 보고 닫습니다.
5. **고정 주기**: 다음에 읽을 시각을 정해 두고 그때까지만 쉽니다. 설비 응답이 느려도 주기가 늘지 않고, 응답이 주기보다 길 때는 밀린 만큼 몰아서 읽지 않습니다(설비에 부담).

**남은 한계** (숨기지 않고 적습니다)
1. **한 설비가 응답을 아예 못 하거나(시간 초과) 연결이 계속 끊기면 그 설비의 수집은 그만큼 줄어든다.** 이것은 고칠 문제가 아니라 통신 장애의 본질입니다. 다른 설비에는 번지지 않습니다.
2. **복구가 최대 4초 늦을 수 있다.** 상한을 더 줄이면 더 빨라지지만 꺼진 설비에 접속을 더 자주 시도합니다. 4초는 그 균형을 잡은 값이고 `--backoff-max`로 바꿀 수 있습니다.
3. **통신 끊김 알람이 꺼진 뒤 약 5초 걸린다.** 연속 3회 실패 후에 발생하므로(재접속 대기 1초, 2초가 사이에 끼어서). 즉시성보다 오탐 방지를 택했습니다.
4. **같은 PC 안의 루프백 통신이다.** 실제 네트워크의 지연 변동, 패킷 손실, 재전송은 없습니다. 지연과 끊김은 TCP 계층이 아니라 시뮬레이터가 응용 계층에서 흉내 낸 것입니다.
5. 시나리오마다 한 번씩(20~35초) 돌린 값이라 통계적 신뢰 구간은 없습니다. 경향과 동작을 확인하는 용도입니다.

## 2. 설비 대수를 늘린 부하 시험

### 방법
- 가상 설비 N대를 **한 프로세스 안**에 서버 N개로 띄우고(설비마다 프로세스를 따로 띄우면 이 PC에 부담이 커서), 수집기는 **진짜 `python -m collector`를 별도 프로세스**로 띄웁니다. 폴링 간격은 기본값 0.5초입니다.
- 접속이 끝나도록 6초를 기다린 뒤 30~60초 동안 잽니다. 수집기의 **CPU와 메모리는 1초마다** 윈도우 API로 읽고, **수집 간격은 DB에 저장된 측정값의 시각**으로 계산합니다(수집이 실제로 빠졌는지 보려고, 프로그램이 스스로 세는 숫자는 믿지 않았습니다).
- 웹 방송을 켜고 **WebSocket 접속자 1명**을 붙여 메시지 수와 크기를 잽니다.
- 도구: `tools/loadtest.py`

### 결과: 개선 전 -> 개선 후

| 설비 수 | 저장 (초당) | 수집 간격 중앙값 / 최대 | 수집기 CPU 평균 (최고) | 메모리 | 이벤트·알람 | 웹 방송 초당 (접속자 1명) | state 메시지 한 개 |
|---|---|---|---|---|---|---|---|
| 6대 | 11.8 -> **12.0** | 0.506 / 0.520 -> **0.500 / 0.528** | 0.5% -> 0.8% (3.1% 같음) | 26MB -> 26MB | 없음 | 19KB -> **5.6KB** | 16KB -> **2.8KB** |
| 30대 | 59.0 -> **60.0** | 0.511 / 0.533 -> **0.500 / 0.545** | 1.8% -> 2.8% (4.7% -> 7.8%) | 30MB -> 28MB | 없음 | 93KB -> **27KB** | 78KB -> **13.1KB** |
| 60대 | 117.0 -> **120.0** | 0.511 / 0.539 -> **0.500 / 0.539** | 2.6% -> 2.9% (6.2% 같음) | 32MB -> 31MB | 없음 | 187KB -> **54KB** | 156KB -> **25.9KB** |
| 100대 | 194.9 -> **200.1** | 0.513 / 0.536 -> **0.500 / 0.541** | 5.5% -> 4.6% (9.4% 같음) | 35MB -> 34MB | 없음 | 311KB -> **89KB** | 260KB -> **42.9KB** |

- 모든 경우에 **설비별 측정값 수가 같았습니다**(예: 100대에서 모두 80~81개, 측정 시작·끝 시각에 따른 1개 차이). 어느 설비도 빠지지 않았다는 뜻입니다.
- **저장 개수가 이상적인 값(설비 수 x 2)과 같아졌고**, 수집 간격 중앙값이 정확히 0.500초가 된 것이 고정 주기의 효과입니다. 최대 간격(0.53~0.55초)은 이전과 같은 수준이라 흔들림이 늘지 않았습니다.
- 설비를 엇갈려 읽으니 이벤트 루프가 깨어나는 횟수가 늘어서인지 **CPU는 30대 이하에서 이전보다 약간 높게(1~2%p) 나왔고 100대에서는 낮게 나왔습니다.** 각각 한 번씩 잰 값이라 측정마다 1%p 안팎으로 흔들리므로 "달라졌다"고 말하기는 어렵고, 어느 경우든 5% 이하로 여유가 큽니다.
- 웹 방송 크기는 설비당 약 2.6KB에서 **약 0.43KB로 6분의 1**이 되었습니다.
- 30대 항목은 요구한 "가상 설비 30대 동시 수집"의 답이고, 60·100대는 어디까지 여유가 있는지 보려고 더했습니다.

### 해석

**잘 버틴 것**
1. 수집 자체는 100대까지 **병목이 아니었습니다.** 이벤트 루프가 설비마다 하나의 작업(워커)을 돌리는 구조(asyncio)라서, 대기하는 동안 다른 설비를 읽습니다. 설비마다 스레드를 만들지 않아 메모리도 거의 늘지 않았습니다(6대 26MB -> 100대 34MB).
2. 저장은 측정값마다 즉시 기록(commit)하는데도, 초당 200건까지 수집 간격이 흔들리지 않았습니다(최대 0.541초).

**처음 측정에서 찾은 약점과 처리 결과**
| 약점 | 처리 |
|---|---|
| 수집 주기가 `응답 시간 + 0.5초`라 설비가 느리면 주기가 늘어남 | **고정 주기**로 변경, 설비별 시작 엇갈림 (시험 13개) |
| 복구가 최대 8초 늦을 수 있음 | 재접속 대기 상한 **4초**로 줄임 (`--backoff-max`) |
| 웹 방송 `state` 메시지가 설비 수에 비례해 큼 (100대 260KB) | 패킷 기록을 방송에서 빼고 `/api/packet`으로 **고른 설비 하나만** 가져옴 (43KB) |
| 오래된 측정값을 지우는 정책 없음 | **보관 정책** 추가: 기본 7일(`--retention-days`), 알람은 보존 (시험 12개) |

**여전히 남은 점**
1. **`state` 메시지는 아직 설비 수에 비례해 커진다.** 설비당 약 0.43KB라서 100대에서 43KB, 1초마다 접속자 모두에게 갑니다. 접속자 10명이어도 약 1MB/s로 같은 PC나 사무실 망에서는 충분합니다. 설비가 수백 대이면 바뀐 값만 보내는 방식이 필요합니다.
2. **보관 정책은 장기 가동으로 직접 확인하지 못했다.** 단위 시험(보관 기간 경계, 설비별·덩어리 삭제, 알람 보존, 오류에도 계속 동작)과 가짜 시각으로만 확인했고, 7일을 실제로 돌려 보지는 않았습니다. SQLite 파일은 지운다고 줄지 않고 빈 공간을 다시 쓰므로, 보관 기간 안의 양에서 더 커지지 않는 것이 목표입니다. 측정값 한 건이 DB에서 약 100바이트이므로(체크포인트 뒤 실측, 30·60·100대에서 97~99바이트) 7일 보관 기준 상한은 6대 약 0.7GB, 30대 약 3.6GB, 100대 약 12GB입니다. 오래된 값을 요약해서 줄여 두는 방식(다운샘플 저장)은 만들지 않았습니다.
3. **단일 접속자, 짧은 시간, 같은 PC에서 잰 값이다.** 접속자 여러 명, 몇 시간 이상 돌리는 장기 시험(메모리가 서서히 늘어나는지), 실제 네트워크는 측정하지 못했습니다. 설비 쪽 시뮬레이터도 같은 PC의 CPU를 나눠 쓰므로 수집기 숫자는 약간 불리하게(높게) 나왔을 수 있습니다.

## 다시 재현하는 방법

```bash
python tools/comm_scenarios.py               # 통신 장애 시나리오 전체 (약 3분). 하나만: --only drop
python tools/comm_scenarios.py --only restart --off-seconds 10 --backoff-max 8   # 재접속 상한 비교 (8초 vs 기본 4초)
```
