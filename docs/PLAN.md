# 산업 장비 디지털 트윈 모니터링 계획 (B안, 약 3주)

## 목적
로봇 팔 여러 대의 설비 데이터를 Modbus TCP로 **동시에, 안정적으로** 수집해 시계열로 저장하고,
웹 3D 화면에서 로봇이 데이터대로 움직이며 이상을 표시한다.
한 설비의 통신 장애가 다른 설비에 번지지 않게 설계한다.

## 구성
```
[가상 PLC x6: ARM-01 :5021 ... ARM-06 :5026]
        │ Modbus TCP (설비별 별개 연결)
        ▼
[수집 서버 (Python, 비동기)]  설비별 재접속·타임아웃·오류 처리
        │                 │
        ▼                 ▼
 [시계열 저장]      [알람 판정·확인(ACK)]
        └────── WebSocket ──────▶ [웹 대시보드: Three.js 3D + 제조 스타일 화면]
```

## 결정 사항
| 항목 | 결정 | 이유 |
|---|---|---|
| 수집·시뮬레이터 언어 | Python | 이 PC의 스마트 앱 컨트롤이 새로 빌드한 .NET 파일을 막음 (archive/csharp-prototype 참고) |
| Modbus 구현 | 라이브러리 없이 소켓으로 직접 | 패킷 구조·바이트 처리 역량을 보여주기 위함 |
| 설비 연결 | 설비마다 별개 프로세스·포트·연결 | 장애 격리 시연 |
| 3D 화면 | 웹 (Three.js 0.170.0, `web/vendor/`에 보관) | 브라우저 안에서 동작, 이 PC의 차단과 무관. 외부 주소에 의존하지 않고 해시로 변조 확인. 기본 도형 조립(모델링 안 함) |
| 브라우저 전송 | WebSocket을 표준 라이브러리만으로 직접 구현 | 표준 라이브러리에 없고, 내려받을 것이 없으며, 규격 이해를 보여 줄 수 있음. 한계: 조각난 메시지 미지원 |
| 시계열 저장 | SQLite (표준 라이브러리)로 구현 완료 | 내려받을 것이 없고 이 규모에 충분. InfluxDB는 필요해지면 허락 후 검토 |
| 이동 로봇(AGV) | 화면 연출로 구현 (서버가 읽는 장치는 아님) | 코어 완료 후 선택 사항이었음. 움직임은 연출이지만 호출 시점은 실제 생산 카운트(팔레트 4개 적재)에서 옴. 판단은 `web/agv_logic.js`로 분리해 Node로 시험 |

## 실행
```bash
python simulator/run_all.py                 # 로봇 6대 (과열을 빨리 보려면 --heat-rate 1.5)
python simulator/modbus_sim.py --name ARM-01 --port 5021 --verbose   # 1대만
python -m collector                         # 수집 서버 (로봇 6대가 떠 있어야 함)
python -m collector --interval 0.2 --timeout 0.5 --report 3
python -m collector --db :memory:           # 저장하지 않고 수집만 (기본은 data/factory.db에 저장)
python -m collector.tools alarms            # 닫히지 않은 알람 (--all 이면 이력)
python -m collector.tools ack 3 --by 홍길동  # 알람 확인(ACK)
python -m collector.tools production --minutes 10
python -m collector.tools events / samples ARM-01
python -m collector.tools alarms --detail   # 알람 내용을 줄 아래에 함께 표시
python -m collector --web-port 8080         # 웹 화면 포트 바꾸기 (기본 8000), --no-web 이면 끔
# 웹 화면: 수집기를 켠 뒤 브라우저에서 http://127.0.0.1:8000/ 을 연다
python -m unittest discover -s tests -v     # Python 시험 308개 (Node 시험, 시험 도구 시험 포함 실행)
node --test "tests/js/*.test.mjs"           # JS 시험 76개만 따로 (폴더가 아니라 파일 패턴을 줘야 함)
```

## 레지스터 맵 (설비마다 동일, Holding Register, 주소 0부터)
| 주소 | 내용 | 단위·값 |
|---|---|---|
| 0 | 관절1 각도 | 0.1도 |
| 1 | 관절2 각도 | 0.1도 |
| 2 | 집게 | 0 열림, 1 닫힘 |
| 3 | 로봇 단계 | 0 대기, 1 접근, 2 집기, 3 이동, 4 놓기, 5 복귀 |
| 4 | 상자 감지 | 0/1 (상자 도착 시 0.6초간 1) |
| 5 | 생산 카운트 | 누적 (65536에서 0으로) |
| 6 | 온도 | 0.1도 |
| 7 | 상태 | 0 정상, 1 주의, 2 이상 |
| 8 | 마지막 사이클 시간 | 0.1초 |
| 9 | 컨베이어 속도 | mm/s (이상 시 0) |

지원 기능 0x03만 지원. 그 외 기능은 예외 0x01, 범위 밖 주소는 예외 0x02.

## 로봇 사이클 (시뮬레이터 동작)
대기 → 접근(1.5s) → 집기(0.8s) → 이동(2.0s) → 놓기(0.8s) → 복귀(1.5s), 한 사이클 약 6.6초.
- 상자는 5~11초 간격으로 도착한다 (사이클보다 길어서 로봇이 쉬는 시간이 생김).
- 놓기가 끝나면 생산 카운트 +1.
- 온도: 움직일 때 오르고 쉴 때 내림. 65도 주의, 80도 이상(정지), 70도 이하로 식으면 복구.

## 수집 서버 동작 규칙
- 설비마다 워커 1개가 자기 연결과 상태를 따로 관리한다 (한 설비의 장애가 다른 설비에 번지지 않음).
- 오류 4종: 시간 초과, 연결 끊김, 규격 위반(깨진 패킷), 설비 예외 응답.
  앞의 셋은 연결을 닫고 재접속, 예외 응답은 연결을 유지한 채 다음 주기에 재시도.
- 재접속 대기: 1초에서 시작해 2배씩 늘어 최대 4초(`--backoff-max`, 7단계 실측 전에는 8초), 읽기에 한 번 성공하면 1초로 복귀.
- 수집 주기: 고정 주기(다음 읽을 시각을 정해 두고 그때까지만 쉼, 밀리면 몰아 읽지 않음) + 설비별 시작 엇갈림.
- 끊김은 두 경로로 감지한다: 읽는 도중이면 `read_failed`, 폴링 사이에 연결이 리셋되면 `disconnected`.
- 끊긴 설비의 마지막 값은 현재 값이 아니다: `data_age`로 경과 시간을 알 수 있고 요약에는 "값은 오래됨"으로 표시한다.
- Windows는 닫힌 포트 접속을 바로 거부하지 않고 재시도해서 제한 시간 안에는 시간 초과로 나타날 수 있다 (둘 다 같게 처리).

## 저장·알람 규칙
| 알람 | 중요도 | 발생 조건 |
|---|---|---|
| EQUIPMENT_FAULT | P1 | 설비가 상태 '이상'(정지)을 보고 |
| COMM_LOST | P1 | 통신 실패가 연속 3회 이상 (복구되면 바로 해제) |
| TEMP_WARNING | P2 | 설비가 상태 '주의'를 보고 |
| COUNTER_RESET | P3 | 생산 카운트가 줄어듦 (65536 한 바퀴는 제외) -> 설비 재시작 추정 |

- 같은 설비·종류의 알람이 열려 있으면 새로 만들지 않고 값만 갱신 (중복 방지).
- 조건이 사라져도 3초 동안 계속 사라져 있어야 해제 (기준선 근처에서 켜졌다 꺼졌다 하는 것을 막음).
- 해제된 지 60초 안에 같은 알람이 다시 발생하고 그 알람을 아직 아무도 확인하지 않았다면, 새로 만들지 않고
  기존 알람을 다시 열면서 반복 횟수를 올린다 (`--reopen-window`로 조절). 최초 발생 시각은 유지하고,
  마지막 발생 시각과 최신 값·내용을 갱신한다. 이미 확인된 알람은 다시 열지 않고 새 알람으로 만든다
  (확인한 사람이 재발생을 놓치면 안 되므로).
- 이전 버전으로 만든 DB는 열 때 새 열(repeat_count, last_raised_at)을 자동으로 추가한다 (기존 데이터 보존).
- 확인(ACK)과 해제는 독립. 해제돼도 사람이 확인하기 전에는 닫히지 않음.
  상태: 활성·미확인 -> 활성·확인됨 -> 종료 / 활성·미확인 -> 해제됨·미확인 -> 종료.
- 알람 상태는 모두 DB에 있어서 수집 서버를 다시 켜도 열린 알람을 이어 받는다.
- 생산량은 카운트 증가분을 더하되, 설비 재시작으로 카운트가 줄면 재시작 후 센 개수만 더한다.
- 시연용 과열 설정(--heat-rate 6)처럼 온도가 70~80도 사이를 빠르게 오가도, 확인 전까지는 알람이 종류당 한 줄로
  묶이고 횟수만 올라간다. 기본 설정에서는 65도에 닿기까지 약 5분이 걸려 훨씬 차분하다.
- 측정 (깨끗한 환경, 다른 포트·임시 DB, 같은 조건의 로봇 3대 세트 두 벌을 동시에 60초): 묶기 끔(--reopen-window 0)
  알람 27행, 묶기 켬 6행. 발생 횟수 합은 두 쪽 모두 27로 같아서 묶어도 발생 이력은 사라지지 않는다.
  한 번씩만 돌린 값이고 과열을 빠르게 만든 극단 설정이라, 실제 줄어드는 비율은 설정에 따라 달라진다.
- 시연·시험 주의: 시뮬레이터는 사용 중인 포트(5021~5023)에서는 시작을 거부한다. 윈도우는 같은 포트에 두 번째
  서버가 오류 없이 붙을 수 있어서 수집기가 어느 로봇에 붙을지 알 수 없었기 때문이다. 포트로 프로세스를
  종료할 때는 내가 띄운 것인지 먼저 확인한다 (명령줄과 시작 시각을 본다).

## 화면용 서버 기능 (패킷·이력·지표·확인 명령)
- **패킷 기록**: 클라이언트가 한 번 주고받을 때마다 보낸·받은 바이트와 오류를 남긴다. 마지막 교환(`last`)과
  마지막 실패(`last_failed`)를 따로 둬서, 실패 직후 정상 교환이 와도 실패한 바이트를 볼 수 있다.
  필드별 해석과 함께 `/api/packet?device=`로 고른 설비 하나만 가져간다(`state` 방송에는 싣지 않음: 설비 수에 비례해 커져서).
- **조회 주소** (GET/HEAD만, JSON): `/api/history?device=&minutes=(1~1440)&points=(20~2000)`,
  `/api/events?limit=`, `/api/alarms?all=1`, `/api/packet?device=`. 숫자는 아스키 숫자만 받고(아랍 숫자·`--3`·`+5` 거절),
  모르는 설비는 404, 잘못된 값은 400, 내부 오류는 500(내용은 로그에만, 응답에는 안 나감).
  `/api/` 아래는 정적 파일로 넘어가지 않는다.
- **지표(KPI)**: 가동률 = 이상이 아닌 상태로 읽은 표본 / 읽었어야 할 표본(수집 공백은 가동 안 한 것으로 계산,
  설비의 첫 표본 이전은 제외, 최대 100%). 생산량은 카운트 한 바퀴·재시작 보정 포함. 통신 성공률·평균 응답·
  재접속은 서버를 켠 뒤 누적. 계산은 5초에 한 번만 다시 한다. `hello`와 `state`에 `kpi`, `hello`에 최근 이벤트 30개.
- **확인 명령** (WebSocket 텍스트): `{"type":"ack","id":알람번호,"by":"이름"}` -> 그 접속에만
  `ack_result`로 답하고, 모든 화면에는 `alarm`(acked)이 간다. 이미 확인된 알람은 `ok:false`.
  이름은 1~20자·제어문자 없음, id는 양의 정수(bool 거절). 명령 하나 4096바이트 이하,
  한 접속당 5초에 20개 이하(넘으면 1008로 끊음). 잘못된 입력은 `error`로 답하고 접속은 유지한다.
  명령 처리 중 예외는 로그에만 남기고 화면에는 일반 문구만 보낸다.
- 시험: 시험 251개가 3회 연속 통과, 새 코드에 변이 17개(경계 바꾸기, 검사 끄기 등)를 넣어 모두 시험이 잡았다.
  실제 실행(격리 포트·임시 DB): 알람 발생 -> WebSocket으로 확인 -> 두 번째 확인 거절 -> 쓰레기 입력 오류 답 확인.

## 한계 (README에도 같은 내용을 적었다)
- 실제 설비·PLC 없이 시뮬레이터 기반이다. 로봇 동작은 정해진 순서대로 만든 값이다.
- 3D는 기본 도형만 조립했다 (외부 모델 파일 없음). 사진 같은 질감과 거울 반사는 없고, 빛 번짐은 있으나 약한 PC에서는 느릴 수 있어 끌 수 있다.
- AGV와 벽 모니터는 화면 연출이다 (서버가 읽는 장치가 아님). 호출 시점과 모니터 숫자는 실제 수집값. 로봇 모양(관절 팔/스카라)은 설비 이름의 홀짝으로 화면이 정한다.
- 통신·부하 시험은 같은 PC의 루프백, 접속자 1명, 20~60초. 7일 보관 정책은 단위 시험으로만 확인했다.
- C/C++, Qt, 임베디드 요건은 채우지 못한다.
